# 0x0049bcb0-0x0049bce8 Critical Section API Wrappers

## Status

- Disposition: reconstructable utility/runtime-adjacent synchronization support.
- Entity kind: tiny Win32 `CRITICAL_SECTION` wrapper helpers.
- Confidence: strong for API behavior and exact byte boundaries; medium for final source-file placement.
- Likely source module: [UID:0000LI][Monitor](by-file/Monitor.md)
- Rebuild handling: reconstructable synchronization helper family. Keep C++ blank because the original source placement and wrapper type names are still not final-source quality.

## Behavior

These are tiny thiscall-style wrappers around Win32 critical-section APIs. They likely support a simple critical-section utility object or compiler-emitted static critical-section cleanup path.

`0x0049bcb0` is the only helper IDA currently promotes as a direct function in `.text`. `0x0049bcc0` is reached from a helper at `0x0060c0e0`, which loads `stru_67A9A4` and jumps into the delete wrapper. The enter/leave wrappers are present as aligned callable bodies but have no direct xrefs in the current IDA database.

## Evidence Notes

- IDA MCP decompiles `0x0049bcb0` as `InitializeCriticalSection(lpCriticalSection); return lpCriticalSection;`.
- IDA MCP disassembly shows `0x0049bcc0`, `0x0049bcd0`, and `0x0049bce0` as `push ecx; call ds:<CriticalSection API>; ret` wrappers.
- IDA MCP xrefs show `0x0049bcb0` called by `0x00419ec5` and `0x0049bcc0` jumped to by `0x0060c0e5`; no direct xrefs were found for `0x0049bcd0` or `0x0049bce0`.

The wrappers are source-reconstructable as small Win32 synchronization helpers or static helper functions backing local critical-section objects. The generated C++ block stays blank until original helper names and placement are stronger.
