## Evidence

- Live IDA MCP recheck on 2026-06-05 confirms exact `DATFile` method starts and half-open ranges from `0x0049c130-0x0049c15a` through the scalar deleting destructor at `0x0049d280-0x0049d2cc`; `0x0049d2cc-0x0049d2d0` is four `CC` bytes before the next function.
- Live IDA MCP recheck on 2026-06-05 confirms the intra-span non-method/support functions at `0x0049c540`, `0x0049c570`, `0x0049c700`, and the manager/resolver/vector sequence from `0x0049c800` through `0x0049d275`, so this page is an aggregate and not a single contiguous method body.
- Live IDA MCP decompilation on 2026-06-05 confirms the constructor calls the base `File` constructor, installs `DATFile::vftable`, and clears object dwords at `+0x4` and `+0x8`; the destructor/scalar deleting destructor clear the active entry/container fields and restore the base `File` vtable before base teardown.
- Live IDA MCP vtable read on 2026-06-05 confirms `DATFile::vftable` at `0x00618924` targets the scalar deleting destructor, base/file runtime slots, `Open`, `Close`, `Tell`, `Seek`, `GetSize`, `Read`, `ReadLine`, and `ReadLineRaw`.
- Live IDA MCP caller counts on 2026-06-05 confirm broad consumer fan-in: constructor 83 callers, `Open` 67, `Read` 131, `ReadAllEntries` 87, `ReadAllEntriesAlt` 6, and `OpenByIndex` 2; the scalar deleting destructor is referenced through the vtable data slot at `0x00618924`.
- Live IDA MCP callees on 2026-06-05 confirm `Open` calls the manager lookup at `0x0049cad0`, `Read` uses `_memmove`, both bulk-entry readers call [UID:00013W][0x004a5e60-0x004a609f.ParseEntries](by-memory/0x004a5e60-0x004a609f.ParseEntries.md), `ReadAllLines` uses string/vector helpers plus the grow helper at `0x0049cc40`, and `OpenByIndex` has no project callees.
- Live IDA MCP decompilation for `Open` and `OpenByIndex` shows 17-byte DAT entry records. Both methods set the current absolute payload offset from the current record's first dword and compute payload size from the next record/sentinel's first dword at `record + 0x11`.
- IDA MCP `lookup_funcs` on 2026-05-22 confirmed function sizes for `0x0049c130`, `0x0049c180`, `0x0049c4a0`, `0x0049c4f0`, and `0x0049c720`.
- IDA MCP `callees` confirmed `0x0049c180` calls `_DATFileMgr::FindEntryByName` at `0x0049cad0`.
- IDA MCP `callees` confirmed `0x0049c4a0` calls [UID:00013W][0x004a5e60-0x004a609f.ParseEntries](by-memory/0x004a5e60-0x004a609f.ParseEntries.md) at `0x004a5e60`.
- IDA MCP recheck on 2026-05-25 confirmed [UID:00013W][0x004a5e60-0x004a609f.ParseEntries](by-memory/0x004a5e60-0x004a609f.ParseEntries.md) has only the two `DATFile` bulk-reader callers at `0x0049c4d4` and `0x0049c524`; decompilation shows both wrappers only compute `GetSize() >> 1`, read eight bytes, and dispatch to the helper.

## Ownership Decision

This range belongs in `archive/DATFile.cpp`. It should not be placed with higher-level image, tile, effect, or map loaders, even though those callers rely on it. Manager-side lookup, mapping, and [UID:0000T0][HasDATEntry_49C700](by-global/HasDATEntry_49C700.md) belong in the companion [UID:0000IO][DATFileMgr](by-file/DATFileMgr.md) module.

[UID:00013W][0x004a5e60-0x004a609f.ParseEntries](by-memory/0x004a5e60-0x004a609f.ParseEntries.md) should be treated as private/static-style support code in the same `archive/DATFile.cpp` module, not as a separate project file.
