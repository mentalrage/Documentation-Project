## Owner And Signature

The current source-facing signature is:

```cpp
void FontStyle::ClearRules();
```

IDA shows a `__thiscall` method that receives `this` in `ecx` and returns no value. The method only touches the rule-vector triplet inside the 0x20-byte [UID:0001UN][FontStyleLayout](by-type/by-struct/FontStyleLayout.md), so the `ClearRules` name is strongly supported even though IDA still names the function `sub_4536E0`.

## Behavior

This method releases the `FontStyle` rule-vector backing allocation and resets the vector triplet at object offsets `+0x14`, `+0x18`, and `+0x1c`.

| Object offset | Meaning |
| --- | --- |
| `+0x14` | `rulesBegin` allocation/user pointer |
| `+0x18` | `rulesEnd` |
| `+0x1c` | `rulesCapacity` / allocation end |

If `rulesBegin` is null, the method returns without touching the object. Otherwise, it checks whether the rounded vector span `(rulesCapacity - rulesBegin) & 0xfffffff0` is at least `0x1000`. Large spans use the MSVC aligned-allocation header convention: the true allocation base is read from the dword immediately before `rulesBegin`, and the header gap must be at most `0x1f`. Failure calls `_invalid_parameter_noinfo_noreturn`.

After validation, the method frees the selected allocation pointer through `sub_5C7526`, then zeros `rulesBegin`, `rulesEnd`, and `rulesCapacity`.

## Reconstructed C++ Candidate

```cpp
void FontStyle::ClearRules()
{
    FontStyleRule* allocation = m_rulesBegin;
    if (allocation == 0)
        return;

    if (((reinterpret_cast<unsigned char*>(m_rulesCapacity) -
          reinterpret_cast<unsigned char*>(m_rulesBegin)) & ~0x0f) >= 0x1000) {
        unsigned char* base =
            reinterpret_cast<unsigned char**>(m_rulesBegin)[-1];
        if (reinterpret_cast<unsigned char*>(m_rulesBegin) - base - 4 > 0x1f)
            _invalid_parameter_noinfo_noreturn();
        allocation = reinterpret_cast<FontStyleRule*>(base);
    }

    FreeHeapBlock(allocation);
    m_rulesBegin = 0;
    m_rulesEnd = 0;
    m_rulesCapacity = 0;
}
```

The final source can express this more simply if the compiler/runtime vector destructor is allowed to own the aligned-allocation guard. Keep the guard documented here because it is present in the binary.
