## Address Range

`0x0048f6d0-0x0048fc96`, ending before the IDA-modeled `sub_48FCA0` at `0x0048fca0`.

IDA does not currently model this start as a function, but live IDA disassembly decodes a normal stack-frame prologue followed by `__alloca_probe`, matching a large source-authored parser.

## Behavior

This helper appears to be a Netsgo-style startup/authentication parser. It expects a long fixed command-line form, validates service/version-like markers, resolves a host name or dotted address, stores browser/launcher launch data and connection target fields into the startup-state block, and terminates through localized error dialogs on invalid data.

On the success path recorded by the legacy report, it writes the resolved address to `param_1 + 0x2915b4`, numeric fields to `param_1 + 0x2916c4` and `param_1 + 0x2916c8`, copies a reconstructed browser command-line string to `param_1 + 0x2916f0`, then sets the shared startup-ready/state fields.

## Evidence

- Legacy Wave2 report records `FUN_0048f6d0` as `0x0048f6d0 .. 0x0048fc95`, with no live Wave2 method/global resolution.
- IDA live disassembly shows the function begins with `__alloca_probe` for a `0x191c` stack frame, then calls `GetCommandLineW`, `_wcscpy_s`, `_wcschr`, `WideCharToMultiByte`, `gethostbyname`, `MessageBoxW`, `PostQuitMessage`, and `__loaddll`.
- The call mix and side effects match a product startup-authentication parser, not a runtime helper.
