## Behavior

Final C++ reconstruction should prefer the source-level delete form:

```cpp
delete g_pCrashTarget;
```

The compiler-level behavior is:

```cpp
if (g_pCrashTarget != nullptr) {
    g_pCrashTarget->ScalarDeletingDestructor(1);
}
```

IDA's decompiler leaves an uninitialized `result` return when the global is null. That is a decompiler artifact of this tiny helper and should not be modeled as meaningful source behavior.

The helper does not clear [UID:0000QN][g_pCrashTarget](by-global/g_pCrashTarget.md) after deleting it; callers that need a null assignment must do that separately.

## Ownership Decision

Assign this exact helper to [UID:0000HG][Application](by-file/Application.md). It is best modeled as application/startup fatal-load cleanup glue that deletes an exception-handler object owned elsewhere.

Ranked ownership analysis:

1. [UID:0000HG][Application](by-file/Application.md) is accepted as the direct source-file parent. The helper sits in the Application lifecycle/startup helper neighborhood, is always paired with Application-owned [UID:0000YV][0x00467380-0x00467391.DestroyDATFileMgr](by-memory/0x00467380-0x00467391.DestroyDATFileMgr.md), and all 22 callers are fatal image/resource load exits that immediately display `Error on ... File!` messages. Application owns process startup/shutdown/fatal UX policy, currently clears the `85/85` parent gate at `86/90`, and is already the accepted parent for the sibling DAT manager cleanup helper.
2. [UID:0000J8][ExceptionHandler](by-file/ExceptionHandler.md) remains the object/global owner but is rejected as the direct helper owner. IDA confirms ExceptionHandler owns normal `g_pCrashTarget` lifecycle through constructor/destructor/filter code, while `0x004673a0` has no callers from the ExceptionHandler method cluster, is outside the `0x004ab480-0x004ac89a` diagnostics range, does not clear the singleton, and is used only in paired Application/resource fatal-load cleanup sites.
3. A new `ApplicationFatalCleanup.cpp` or `FatalLoadCleanup.cpp` grouping is not recommended now. If created, its likely contents would be only the narrow deletion-helper trio `0x00467380`, `0x004673a0`, and `0x004673c0`; adjacent helpers immediately cross into Application accessors, callback support, `PasswordError` metadata, and Application DAT-series startup policy. That scope is too small and less defensible than keeping these wrappers near the Application startup/failure policy that calls and surrounds them.
4. Image-library source files such as [UID:0000L5][MapTileImageLib](by-file/MapTileImageLib.md), [UID:0000JY][HumanImageLib](by-file/HumanImageLib.md), [UID:0000O7][StaticObjImageLib](by-file/StaticObjImageLib.md), [UID:0000IY][EffectObjImageLib](by-file/EffectObjImageLib.md), and [UID:0000LR][NewHumanImageLib](by-file/NewHumanImageLib.md) are consumers, not owners.
