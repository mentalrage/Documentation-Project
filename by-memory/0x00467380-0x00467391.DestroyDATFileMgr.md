## Behavior

Final C++ reconstruction should prefer the source-level delete form:

```cpp
delete g_pDATFileMgr;
```

The compiler-level behavior is:

```cpp
if (g_pDATFileMgr != nullptr) {
    g_pDATFileMgr->ScalarDeletingDestructor(1);
}
```

IDA's decompiler leaves an uninitialized `result` return when the global is null. That is a decompiler artifact of this tiny helper and should not be modeled as meaningful source behavior.

The helper does not clear [UID:0000QQ][g_pDATFileMgr](by-global/g_pDATFileMgr.md) after deleting it; callers that need a null assignment must do that separately.

## Ownership Decision

Assign this exact helper to [UID:0000HG][Application](by-file/Application.md). It is best modeled as application/startup fatal-load cleanup glue that deletes an archive manager object owned elsewhere.

Ranked ownership analysis:

1. [UID:0000HG][Application](by-file/Application.md) is accepted as the direct source-file parent. The helper sits in the Application lifecycle/startup address neighborhood, is adjacent to Application-owned/global startup helpers, participates in fatal resource-load exits from image-library startup constructors, and pairs every time with the exception-handler cleanup helper before fatal error reporting. Application currently clears the `85/85` parent gate at `86/90`, and this child clears it at `88/91`.
2. [UID:0000IO][DATFileMgr](by-file/DATFileMgr.md) remains the object/singleton owner but is rejected as the direct helper owner. IDA confirms the DAT manager constructor/destructor/clear helpers own normal `g_pDATFileMgr` lifetime, while `0x00467380` is an external fatal-unwind wrapper, has no DAT manager callers, is outside the archive manager text cluster, and is always paired with unrelated crash-handler cleanup at fatal image/resource-load exits.
3. A new `ApplicationFatalCleanup.cpp` or `FatalLoadCleanup.cpp` grouping is not recommended now. If created, its likely contents would be only the narrow deletion-helper trio `0x00467380`, `0x004673a0`, and `0x004673c0`; adjacent helpers immediately cross into Application accessors, callback support, `PasswordError` metadata, and Application DAT-series startup policy. That scope is too small and less defensible than keeping the helpers near the Application startup/failure policy that calls and surrounds them.
4. Image-library source files such as [UID:0000L5][MapTileImageLib](by-file/MapTileImageLib.md), [UID:0000JY][HumanImageLib](by-file/HumanImageLib.md), [UID:0000O7][StaticObjImageLib](by-file/StaticObjImageLib.md), [UID:0000IY][EffectObjImageLib](by-file/EffectObjImageLib.md), and [UID:0000LR][NewHumanImageLib](by-file/NewHumanImageLib.md) are consumers, not owners. Their constructors/table loaders call the shared cleanup helper on fatal resource validation failures; they do not own the DAT manager singleton or the shared cleanup function definition.
