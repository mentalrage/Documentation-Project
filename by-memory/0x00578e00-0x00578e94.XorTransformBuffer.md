## Covered Range

| Range | Current name | Notes |

| `0x00578e00-0x00578e94` | `XorTransformBuffer` | Applies repeated-key XOR over dword blocks plus one to three trailing bytes. |

IDA MCP confirms `0x00578e00` as a function start with size `0x94`; the exclusive end is `0x00578e94`.

## Behavior

The helper:

- Iterates over `len >> 2` four-byte blocks.
- XORs each source dword with `keyWords[index % step]` and writes the result to the destination.
- Handles `len & 3` trailing bytes using the next key word.
- Returns the last calculated low byte/value, which callers currently ignore.

`src` and `dst` may alias. Both `Socket::TransformFramePayload` and `Socket::BuildEncryptedPacket` use in-place calls after the first transform pass.

## IDA MCP Evidence

The 2026-06-06 live IDA MCP refresh confirms:

- `lookup_funcs`: `sub_578E00` starts at `0x00578e00` with size `0x94`; sibling callers are `sub_578B20` at `0x00578b20` size `0x120` and `sub_578C40` at `0x00578c40` size `0x1b1`.
- `callers` and `xrefs_to`: six direct call sites, three from inbound [UID:0001I3][0x00578b20-0x00578c40.SocketTransformFramePayload](by-memory/0x00578b20-0x00578c40.SocketTransformFramePayload.md) at `0x00578bb2`, `0x00578bed`, and `0x00578c26`, and three from outbound [UID:0001I4][0x00578c40-0x00578df1.SocketBuildEncryptedPacket](by-memory/0x00578c40-0x00578df1.SocketBuildEncryptedPacket.md) at `0x00578d27`, `0x00578d67`, and `0x00578d99`.
- `callees`: no internal or import callees; this is a leaf transform routine.
- Key/global xrefs: `g_packetTransformLut` at `0x0066fe58` is populated from `Socket::HandleSocketCommand` and adjacent setup code; primary table `0x0069ba64` is referenced by `BuildHandshakeBlock`, inbound transform, and outbound transform; alternate table `0x0069ba94` is referenced by nonce/string-key setup plus both transform callers.
- Boundary evidence: disassembly from `0x00578df1` shows alignment before `0x00578e00`; disassembly at `0x00578e94` shows alignment and then the unrelated `UNL.DLL` helper beginning at `0x00578ea0`.

IDA MCP `decompile` emits a five-argument `__stdcall` helper: source address, destination address, byte length, dword key table pointer, and key-table stride/count. The fast path loops over `length >> 2`, uses `blockIndex % stride` to select a key dword, XORs one source dword into the destination, then handles one, two, or three tail bytes from the next key dword.

Disassembly matches the decompiler: the dword loop uses `idiv [arg_10]` for modulo, reads `keyWords[edx]`, XORs `[ecx]`, stores through `esi`, then tests `length & 3`. Tail cases write either one byte, one word, or one word plus the third byte.

## Signature Caveat

IDA decompiles `0x00578e00` as a byte-returning helper taking integer-address source, destination, key pointer, and stride arguments. Existing generated projections remain inconsistent:

- `recovered/XorTransformBuffer_00578E00.cpp` defines `std::uint8_t XorTransformBuffer(std::uint32_t* src, std::uint32_t* dst, std::uint32_t len, int keyPtr, std::uint32_t step)`;
- `class_Socket.cpp` declares it as `extern void XorTransformBuffer(...)`;
- `Socket::BuildEncryptedPacket` passes byte pointers for payload and key arguments.

Normalize the helper prototype before source migration. The behavior is byte-buffer oriented even though the fast path processes full dwords, and all live callers ignore the low-byte return.

The key pointer arguments are dword-oriented: command `13` fills `g_packetTransformLut` at `0x0066fe58` as 256 dwords, and the primary/alternate table pointers passed from Socket point at [UID:0000TG][PacketTransformGlobals](by-global/PacketTransformGlobals.md) rather than packet-buffer cursors.
