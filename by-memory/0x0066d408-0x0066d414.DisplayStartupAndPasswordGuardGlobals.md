## Evidence

- IDA bytes at `0x0066d408` are `00 04 00 00 01 00 00 00 44 d5 00 00`, matching `xRight = 1024`, `dword_66D40C = 1`, `word_66D410 = 0xd544`, and two zero bytes.
- IDA xrefs to `xRight` are `0x00463da7` and `0x004642f3` in `Application::Initialize`. The write path clamps the width against `0x400` and `0x0f00`, aligns it with `and eax, 0FFFFFFFCh`, then stores it to `xRight`.
- IDA xrefs to `dword_66D40C` are `0x00463dbe`, `0x00463dde`, and `0x005597b4`. Startup keeps the default value unless a candidate value minus one is `<= 2`; presentation code compares it against `1`, uses the non-stretch DirectDraw blit path for that value, and otherwise uses `SetStretchBltMode` with mode `3` for value `2` and mode `4` for the remaining non-`1` value.
- IDA xrefs to `word_66D410` are `0x004657e5`, `0x00465866`, and `0x004658d2`. `SetProtectedPasswordToken` loads it immediately after copying into `word_67A940`, and `ValidateChatInputOrThrowPasswordError` loads the same seed after copying the protected token to a local buffer.
- IDA decompilation shows the password guard transform as `*p++ = seed++ ^ ch` in both encode and decode paths, so `word_66D410` is the initial XOR seed rather than an application/window helper.
