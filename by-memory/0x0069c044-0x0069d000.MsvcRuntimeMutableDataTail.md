# MSVC Runtime Mutable Data Tail

## Summary

- Address range: `0x0069c044-0x0069d000`
- Entity kind: runtime/global-data tail inside IDA `.data`
- Disposition: ignored for NexusTK-owned reconstruction
- Rebuild handling: `third-party/runtime`
- Confidence: very strong for non-NexusTK runtime/library classification and boundaries; strong for internal runtime-family names; medium for exact private CRT/STL symbol spellings

This range is the final writable-data tail in the IDA `.data` segment. B009's 2026-06-19 source-quality reanalysis keeps it ignored, `RECONSTRUCTABLE:FALSE`, `CANONICAL_OWNER:NONE`, blank emitters, and blank C++: it is MSVC CRT/STL/ACRT/SCRT mutable runtime storage plus section-alignment zero-fill, not a NexusTK-authored source object. The previous `FF:4028` byte-count evidence is stale for the executable available in this workspace or reflects a non-raw/runtime-mutated view. ## Heuristic / Inference Reanalysis And Validation

- Runtime classification: keep ignored/non-reconstructable runtime/library data. Direct PE section mapping, hundreds of refs from MSVC runtime/STL/ACRT code islands, startup wrappers, `_Init_locks`, `initialize_pointers`, `__scrt_common_main_seh`, and ACRT lowio access patterns reject a NexusTK-owned source-global cluster.
- Raw byte claim: current raw PE evidence shows zero-filled/unbacked storage. The historical `FF:4028` claim is preserved only as stale or non-raw/runtime-view history.
- Boundary against [UID:0001Q4][0x0069bf98-0x0069c044.SnowLookupDescriptorStorage](by-memory/0x0069bf98-0x0069c044.SnowLookupDescriptorStorage.md): keep the current start. Snow descriptor xrefs end at the `0x0069c040` guard, and successor refs begin at `0x0069c044`.
- End boundary: keep `0x0069d000`. Although `.data` `VirtualSize` ends at `0x0069ce24`, current IDA/coverage model the aligned `.data` segment to `0x0069d000`; `0x0069ce24-0x0069d000` is section-alignment zero tail, not a separate unknown.
- First-address zlib sentinel: best descriptive names are `zlibErrorMessageEmptyStringSentinel` or `zeroFillEmptyStringHead`. Do not create a separate zlib child because the source-owned construct is the `z_errmsg` pointer table already represented by [UID:00028E][0x00671a74-0x00672eb4.Zlib114DataMessagesAndTables](by-memory/0x00671a74-0x00672eb4.Zlib114DataMessagesAndTables.md); the physical byte is linker/zero-fill coalescing.
- `stru_69C050` / `dword_69C110`: document as MSVC/Dinkumware `_Init_locks` lock storage. Best names are `stdInitLocksPrimaryStorage` for `0x0069c048-0x0069c110`, `stdInitLockArray` for `0x0069c050-0x0069c110`, and no independent source name for the end marker at `0x0069c110`.
- `dword_69C12C` / `unk_69C134`: document as `dinkumwareLocaleFacetCleanupState`, `stdFacetTidyRegistry`, and `iosBaseLocaleRuntimeState`. Exact private Dinkumware field spelling is not recovered and is non-blocking because this is external runtime data.
- `0x0069c1a0/0x0069c1a1`: document as second `_Init_locks` and `_Init_atexit` state reached by the startup/cleanup wrappers, not project static storage.
- `0x0069c1d0-0x0069c26c`: document as SCRT encoded Win32 API-pointer cache. It is populated after resolving `Fls*`, critical-section, init-once, event, semaphore, and threadpool API names from runtime `.rdata` strings.
- `0x0069c604` and `0x0069c650/654/658`: document as SCRT startup/TLS/static-guard state. Product-code references are compiler-inserted thread-safe local-static guard accesses, not ownership evidence.
- `0x0069c750/754` and `0x0069ca08`: document as ACRT lowio/stdio/file-handle runtime storage. Reject NexusTK file-manager ownership because the access pattern is standard ACRT lowio `fd >> 6` / `fd & 0x3f` table indexing with `0x30`-byte records.
- `0x0069cd08+`: document as CRT timezone/environment/locale/multibyte storage. Reject product time/calendar ownership because refs are from CRT `tzset`, time conversion, and multibyte/locale functions.
- Owner placement: `CANONICAL_OWNER:NONE` remains correct. [UID:0001QE][client_libraries](by-meta/client_libraries.md) is a support/dependency index, [UID:0001Z8][0x0066d000-0x0069d000.DataSection](by-memory/0x0066d000-0x0069d000.DataSection.md) is a section container, and [UID:0000PC][Zlib](by-file/Zlib.md) owns only the source-level zlib error-message table semantics, not the full target.
- Split decision: no split now. A theoretical `0x0069c044-0x0069c048` zlib empty-string/alignment head would remain a one-byte zero-fill artifact, while internal runtime-family splits would all still be `RECONSTRUCTABLE:FALSE`, `CANONICAL_OWNER:NONE`, blank emitters. A detailed table in this page is the clearer representation.
- First-draft C++ eligibility: not eligible. Any emitted C++ such as `char byte_69C044[0xfbc];`, `static int dword_69C604;`, or private CRT struct declarations would hand-port toolchain/runtime internals into NexusTK source and fight the selected compiler/runtime. Correct rebuild behavior comes from a compatible MSVC CRT/STL/ACRT model plus zlib source, not from this page.
