## Ownership Decision

Treat this as the protected navigation-method cluster of [UID:0000BE][PursuitMessageDialogPane](by-class/PursuitMessageDialogPane.md). The exact receiver/source route is now closed:

- the helpers are `ECX` receiver bodies over fields at `this + 0x26c/+0x270/+0x274/+0x276`;
- `DialogPane` ends at `0x26c`, so the fields are not generic DialogPane state;
- Pursuit-derived constructors across message/menu, TextDialog, and proxy paths initialize the same byte/dword/word/word tail;
- RTTI proves TextDialog and NexonclubProxyDialog directly inherit Pursuit;
- Destination 2 declares the matching protected methods and members without raw offsets or duplicate derived fields.

Historical B012 no-owner/no-emitter reasoning was correct under the then-missing receiver declaration. It is now superseded by the current RTTI/layout controls, while all original negative checks remain useful history.

Rejected alternatives:

- Private `TextDialog` methods: rejected because non-TextDialog action handlers and the Nexonclub proxy callback call the same bodies.
- Private/file-level [UID:0000LA][MessageDialogs](by-file/MessageDialogs.md) helpers: rejected because the bodies use a class receiver and TextDialog/proxy consume them through Pursuit inheritance.
- [UID:0000IT][DialogPane](by-file/DialogPane.md)/[UID:00003T][DialogPane](by-class/DialogPane.md) `DialogPane`: rejected because current base layout does not own the derived-tail packet fields at `+0x26c` and later.
- PacketBuffer, Socket, or ProtocolSend ownership: rejected because writer/send/global APIs are generic callees/dependencies, not the owner of opcode `0x3a` dialog source behavior.
- Three child pages: rejected because the cluster boundaries are already exact and the three tiny methods share one class receiver, packet layout, dependency surface, and source route.
- Padding/runtime: rejected because all three ranges are modeled, called, stack-cookie protected, source-shaped game-code helpers.
