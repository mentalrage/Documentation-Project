# 0x0067a764-0x0067a768 Active MapPane Singleton

## Status

- Disposition: reconstructable NexusTK global-data pointer.
- Entity kind: process singleton pointer / alias correction point.
- Parent global: [UID:0000PR][g_activeMapPane](by-global/g_activeMapPane.md).
- Owner file: [UID:0000L3][MapPane](by-file/MapPane.md).
- Confidence: strong for the address, 4-byte storage, lifecycle writes/clears, and active-map role. The final project spelling of the global remains provisional.

## Storage

`0x0067a764-0x0067a768` is the four-byte storage backing [UID:0000PR][g_activeMapPane](by-global/g_activeMapPane.md).

The weather-state and game-server-config names seen around this address are aliases or misattributions over the same bytes, not independent globals. Weather code checks byte `g_activeMapPane + 0x3f0` before drawing rain or snow overlays; it does not prove a separate weather singleton exists.

## Evidence

- 2026-06-06 IDA MCP `py_eval` reports the data item at `0x0067a764` as a four-byte `.data` slot with bytes `00 00 00 00`; the surrounding `0x0067a75c-0x0067a77c` window is also zeroed.
- The item is not a function and has `360` xrefs across map, minimap, input, targeting, application cleanup, menu, spell, rendering, and weather paths.
- `0x00504110-0x00504521` initializes the map pane, writes `this` to the slot at `0x00504161`, and clears the slot at `0x00504168` on the constructor guard path. The same routine installs `MapPane` vtables, constructs child arrays, initializes render/input state including the byte at `+0x3f0`, registers with the back-pane singleton, and loads map object/nation globals.
- `0x00504530-0x005046c6` is the matching teardown. It restores `MapPane` vtables, unregisters from the back-pane singleton, destroys child panes/layers and vector entries, frees map/nation data, and clears the slot at `0x005046a5` before base teardown.
- `0x00514ac0-0x00514acb` is a tiny clear helper that writes zero to this slot.
- `0x00464e40-0x00464f34` reads the slot during an application transition and calls the `0x005047f0` cleanup/close helper when the singleton is live.
- Additional consumers include minimap construction at `0x00450e43` and broad map-pane users at `0x004244a1`, `0x004523d0`, `0x00452ea9`, `0x00465fef`, `0x00466ae0`, `0x004675ed`, and `0x00467636`.
- Weather refs include `RainingLayerPane::OnPaint` at `0x005c1476`, `RainingLayerPane::DrawRainOnTarget` at `0x005c1814`, `SnowingLayerPane::UpdateAndRenderSnowParticles` at `0x005c1d31`, `SnowingLayerPane::RandomizeSnowParticles` at `0x005c1f56`, and `SnowingLayerPane::RenderSnowParticles` at `0x005c2173`.
- High-fanout reader clusters include target-selection/key navigation functions at `0x005afa10`, `0x005b0290`, `0x005ae730`, `0x005af050`, and `0x005af710`, plus 51 no-function-object refs that include older UI/render helper bodies. These are consumers of the active map-pane pointer, not alternate owners.

## Score Rationale

The score remains `84/90` because the byte range, zero-initialized storage width, constructor write, guard clear, destructor/helper clears, parent global, and representative consumers are all live-verified. Remaining uncertainty is limited to final naming and some unmodeled MapPane field names, so the page stays below final-code reconstruction and keeps the C++ block blank.

## Disposition

Use one project global for this storage, likely `g_activeMapPane`, `g_pMapPane`, or `g_pActiveMapPane`. Do not create a second weather-state global over the same bytes unless later evidence proves a distinct storage address.
