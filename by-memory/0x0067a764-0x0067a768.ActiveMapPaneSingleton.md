# 0x0067a764-0x0067a768 Active MapPane Singleton

## Status

- Disposition: reconstructable NexusTK global-data pointer.
- Entity kind: process singleton pointer / alias correction point.
- Proposed owner: [UID:0000L3][MapPane](by-file/MapPane.md).
- Global doc: [UID:0000PR][g_activeMapPane](by-global/g_activeMapPane.md)
- Confidence: strong for address and broad active-map role.

## Storage

`0x0067a764-0x0067a768` is the `dword_67A764` storage currently documented as `g_activeMapPane`.

The misleading generated weather alias `g_pWeatherState` uses this same storage. Weather code checks byte `g_activeMapPane + 0x3f0` before drawing rain or snow overlays; it does not prove a separate weather singleton exists.

## Evidence

- IDA MCP `py_eval` reports the data item at `0x0067a764` as `dword_67A764`, size `4`, in `.data`.
- IDA xrefs are high-volume across map, minimap, input, targeting, application cleanup, and weather rendering paths.
- Weather refs include `RainingLayerPane::OnPaint` at `0x005c1476`, `RainingLayerPane::DrawRainOnTarget` at `0x005c1814`, `SnowingLayerPane::UpdateAndRenderSnowParticles` at `0x005c1d31`, `SnowingLayerPane::RandomizeSnowParticles` at `0x005c1f56`, and `SnowingLayerPane::RenderSnowParticles` at `0x005c2173`.
- [UID:0000PR][g_activeMapPane](by-global/g_activeMapPane.md) records the broader lifecycle: `0x00504110` writes this storage during map-pane initialization and `0x00504530` clears it during teardown.

## Disposition

Use one source-level global for this storage, likely `g_activeMapPane`, `g_pMapPane`, or `g_pActiveMapPane`. Do not create a second `g_pWeatherState` global over the same bytes unless later evidence proves a distinct storage address.
