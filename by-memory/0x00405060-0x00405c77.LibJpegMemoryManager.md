# IJG libjpeg Memory Manager `0x00405060-0x00405c77`

## Status

- Confidence: strong for `jmemmgr.c` identity.
- Proposed owner: [UID:0000KN][LibJPEG](by-file/LibJPEG.md)
- Source file: `jpeg-6b/jmemmgr.c`
- Evidence basis: obtained official `jpegsrc.v6b.tar.gz` source comparison plus read-only IDA MCP decompile/callee checks on 2026-05-25. `wave3.py` was not executed.

## Range Role

This range implements IJG libjpeg's system-independent pooled memory manager. It is statically linked third-party support code.

The backend calls that actually allocate/free memory are outside this range at [UID:0000W1][0x00406e50-0x00406ed1.LibJpegNoBackingStoreMemoryBackend](by-memory/0x00406e50-0x00406ed1.LibJpegNoBackingStoreMemoryBackend.md). The gap `0x00405c80-0x00406e4f` is not memory-manager code and should not be included in this range; it contains later decompression controller/support code in the libjpeg island.

## Evidence Notes

- `jinit_memory_mgr` references `JPEGMEM` at `0x00671a64`.
- IDA decompilation of `0x00405060` installs the same callback set named in `jpeg-6b/jmemmgr.c`: `alloc_small`, `alloc_large`, `alloc_sarray`, `alloc_barray`, virtual-array request/access helpers, `free_pool`, and `self_destruct`.
- `jinit_memory_mgr` calls the backend initializer at `0x00406ec0`, and allocation/free callbacks in this range call backend functions at `0x00406e50`, `0x00406e60`, `0x00406e70`, `0x00406e80`, and `0x00406ea0`.
