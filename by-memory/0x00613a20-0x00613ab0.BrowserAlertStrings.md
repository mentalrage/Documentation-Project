## Boundary Notes

`0x00613a18-0x00613a1e` is the shared `OK` string and has many UI alert xrefs, so it is not claimed as browser-owned here. The next string group at `0x00613ac4` starts web-board filename/path formatting and should stay with web-board/browser resource docs if researched separately.

## Evidence Notes

- IDA MCP `decompile 0x0046a910` on 2026-05-25 shows `BrowserPane::OnCommand` passing these literal addresses directly to the alert-pane constructor path.
- IDA MCP `xrefs_to` confirms one direct data xref from `BrowserPane::OnCommand` for each browser-specific string: `0x46a97e`, `0x46a9d5`, `0x46aa06`, and `0x46a9ab`.
- A direct IDA bytes/string scan decodes the UTF-16LE strings above and confirms the end-exclusive string boundaries.
- Current `simroot_v2/browser/Browser.cpp` emits `BrowserPane::OnCommand` in the consolidated browser file and still references `g_pBrowserFileLoadText` and `g_pBrowserTimeoutText` in the `BCfl`/`BCto` cases. A current `simroot_v2` search finds those names only as unresolved source identifiers/source-map previews, not as active `global-data` rows with storage ranges. Current IDA evidence still shows direct string literals rather than separate pointer storage.
