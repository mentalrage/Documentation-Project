## Boundary Evidence

Live IDA MCP on 2026-06-08 reports no function object at `0x004d1660` or `0x004d1704`, no direct xrefs to `0x004d1660`, and the following byte boundaries:

```text
0x004d165d-0x004d1660: cc cc cc
0x004d1660-0x004d1704: 55 8b ec ... 5d c2 0c 00
0x004d1704-0x004d1710: cc cc cc cc cc cc cc cc cc cc cc cc
```

The body starts with a normal `push ebp; mov ebp, esp` prologue, ends with `ret 0x0c`, and is followed by twelve `0xcc` alignment bytes before the smaller rectangle-copy raw helper at `0x004d1710`.

## Behavior

The helper reads an ImageFrameTable-style table and projects one frame record into a caller output record with copied payload spans.

Observed disassembly behavior:

- calls the memory-manager accessor at `0x00516030`;
- rejects negative indexes and indexes greater than or equal to the table's 16-bit count at offset `+0x00`;
- selects the 24-byte frame record from the pointer at table offset `+0x08`;
- computes the first payload span as `record[+0x14] - record[+0x10]`;
- allocates that span with `0x00516050`, stores the allocation at output offset `+0x04`, and copies bytes from `record + 0x10` through `0x00516220`;
- computes a width-like field from `record[+0x08] - record[+0x00]` and stores it at output offset `+0x0c`;
- copies the first 16 record bytes into output offset `+0x10`;
- computes the second payload span as `nextRecord[+0x10] - record[+0x14]`;
- allocates and copies that second payload span into output offset `+0x24`;
- stores the second span length at output offset `+0x20`;
- on out-of-range input, clears only output pointers `+0x04` and `+0x24`.

The two span calculations match the sentinel/next-record boundary model already documented for the ImageFrameTable record array.
