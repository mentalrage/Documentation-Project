## Function Role

IDA models this as `sub_4345F0`, size `0x297` / `663` bytes (Verified with int_convert.py). The current half-open range is exact: two `0xcc` padding bytes precede the function at `0x004345ee-0x004345f0`, the source body begins at `0x004345f0`, IDA reports exclusive function end `0x00434887`, and nine `0xcc` padding bytes at `0x00434887-0x00434890` separate this target from successor `sub_434890`.

The function:

- computes token length from token begin/end pointers;
- reports `Unable to parse token length` if the computed length is negative;
- copies short tokens into a stack buffer or long tokens into a temporary string;
- parses the number text;
- stores the parsed numeric value into the output `Json::Value` on success;
- reports `'<token>' is not a number.` on parse failure.

The 2026-06-15 decompile shows the short-token path copying at most 32 bytes into a stack buffer, null-terminating it, and passing it to the local numeric parse helper. Longer tokens are copied into a temporary string object before the same parse helper is called. On success, the parsed 64-bit value is moved into a `Json::Value`-style temporary and assigned to the caller-provided output; on failure, the helper builds the quoted token diagnostic and routes it through the adjacent parse-error reporter.

The formal C++ inline value intentionally uses the validator import directive for the staged JsonCpp source and headers, and the multiline block stays blank. This target should not receive a handwritten or decompiler-shaped body: source-correct reconstruction comes from `third_party_embeds/jsoncpp/src/lib_json/json_reader.cpp`.

## Version Matching Notes

This helper is one of the strongest discriminators between staged JsonCpp candidates:

- `jsoncpp-0.10.6.candidate.zip` does not contain `Unable to parse token length` and does contain `throwRuntimeError("reader error")`.
- `jsoncpp-1.7.2.candidate.zip` contains `Unable to parse token length` and does not contain `reader error`.
- IDA strings contain `Unable to parse token length` and do not contain `reader error`.

This rules out `0.10.6` as an equal candidate and favors a `1.7.x` JsonCpp source family. It does not by itself prove the exact source snapshot, because official `1.7.0` through `1.7.7` spot-checks all share the visible string-level discriminator.

The body also helps reject later `1.7.5+` source:
