# JsonCpp Number Token Parse Helper

## Status

- Address range: `0x004345f0-0x00434887`
- Entity kind: statically linked third-party JsonCpp parser helper
- Confidence: strong for JsonCpp ownership; high for current upstream snapshot candidate, medium for exact upstream function name
- Evidence basis: IDA MCP `lookup_funcs`, `xrefs_to`, and `analyze_funcs` on 2026-05-25 plus local JsonCpp source comparison. `wave3.py` was not executed.

## Function Role

IDA models this as `sub_4345F0`, size `0x297`. It is an `OurReader`/builder-era number-token parse helper in the second JsonCpp parser family. The function:

- computes token length from token begin/end pointers;
- reports `Unable to parse token length` if the computed length is negative;
- copies short tokens into a stack buffer or long tokens into a temporary string;
- parses the number text;
- stores the parsed numeric value into the output `Json::Value` on success;
- reports `'<token>' is not a number.` on parse failure.

## Evidence

- IDA string `Unable to parse token length` lives at `0x0060e730` and is referenced at `0x0043463c` inside this function.
- IDA `analyze_funcs` reports callers from `0x00433d20` and `0x00434430`, both inside the adjacent [UID:0000X8][0x00432e10-0x004345ee.JsonCppSecondParserIsland](by-memory/0x00432e10-0x004345ee.JsonCppSecondParserIsland.md).
- Other strings from this function include `'` at `0x0060e53c` and `' is not a number.` at `0x0060e528`, matching JsonCpp number-token diagnostics.

## Version Matching Notes

This helper is one of the strongest discriminators between staged JsonCpp candidates:

- `jsoncpp-0.10.6.candidate.zip` does not contain `Unable to parse token length` and does contain `throwRuntimeError("reader error")`.
- `jsoncpp-1.7.2.candidate.zip` contains `Unable to parse token length` and does not contain `reader error`.
- IDA strings contain `Unable to parse token length` and do not contain `reader error`.

This rules out `0.10.6` as an equal candidate and favors a `1.7.x` JsonCpp source family. It does not by itself prove the exact source snapshot, because official `1.7.0` through `1.7.7` spot-checks all share the visible string-level discriminator.

The body also helps reject later `1.7.5+` source:

- Upstream commit `094a7d8` added `fixNumericLocaleInput(buffer, buffer + length)` before the stack-buffer `sscanf` path in `OurReader::decodeDouble`.
- IDA decompile of `0x004345f0` shows the stack buffer being copied and null-terminated, then passed directly to the local `sscanf` wrapper without an intervening locale-fix helper.
- Combined with [UID:0000X7][0x00431d50-0x00431f1c.JsonCppOurReaderParse](by-memory/0x00431d50-0x00431f1c.JsonCppOurReaderParse.md) and [UID:0000WY][0x00424630-0x00428b4b.JsonCppValueCore](by-memory/0x00424630-0x00428b4b.JsonCppValueCore.md), this supports the official upstream `b299d3581f4dc670734f1fe1a34fce1282337802` source snapshot as the current best match.
