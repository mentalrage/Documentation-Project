## Evidence

- IDA MCP `py_eval` byte/function audit on 2026-05-27 reports the span in `.text`, not fully padding, with function starts at `0x00419e60`, `0x00419e70`, `0x00419e80`, and `0x00419ec0`.
- IDA MCP decompilation shows each function is a tiny startup wrapper or static object constructor wrapper.
- IDA MCP `xrefs_to` reports only `.rdata` startup initializer table entries for these wrappers: `0x0060d694`, `0x0060d698`, `0x0060d69c`, and `0x0060d6a0`.
- 2026-06-15 live IDA MCP session `a003_objectlist_dispatch_20260615` reconfirmed the wrapper function objects: `sub_419E60` size `0xb`, `sub_419E70` size `0xb`, `sub_419E80` size `0x34`, and `sub_419EC0` size `0x16`; the neighboring [UID:0000W8][0x00419ee0-0x00419ef4.InitializeOleSupport](by-memory/0x00419ee0-0x00419ef4.InitializeOleSupport.md) still begins at `0x00419ee0`.
- Live `xrefs_to` returned exactly one xref for each wrapper, all data refs from the startup initializer table: `0x0060d694 -> 0x00419e60`, `0x0060d698 -> 0x00419e70`, `0x0060d69c -> 0x00419e80`, and `0x0060d6a0 -> 0x00419ec0`; no ordinary code caller was reported.
- Live `analyze_component` confirmed the wrappers are single-basic-block startup entries: the first two call `sub_424850`, the `0x00419e80` wrapper calls `sub_4F4A80` and `_atexit`, and the `0x00419ec0` wrapper calls `sub_49BCB0` and `_atexit`.
