# 0x00514f70-0x005151a9 Map Path Deque Support

## Status

- Disposition: ignored compiler/STL container support for handwritten map path logic.
- Entity kind: template/container helper cluster.
- Primary consumer: [UID:00007Q][MapPane](by-class/MapPane.md)
- Proposed source owner: [UID:0000L3][MapPane](by-file/MapPane.md) should own the pathfinding logic that instantiates this support, but not the helper bodies as handwritten code.
- Confidence: strong for function boundaries and container behavior; medium for the exact source-level container type.
- Rebuild handling: `third-party/runtime`; source should use the map path queue/deque container at the MapPane logic level, not hand-port these MSVC STL-style support bodies as NexusTK product source.

## Covered Ranges

| Range | Current IDA name | Role |
| --- | --- | --- |
| `0x00514f70-0x00515100` | `sub_514F70` | Grows/reallocates an internal segmented pointer map for a deque-like container. |
| `0x00515110-0x005151a9` | `sub_515110` | Appends a two-int coordinate/pair record into the deque-like container, allocating a 16-byte block when needed. |

## Behavior

The first helper doubles a segmented map capacity, allocates aligned storage for map pointers when needed, moves existing map pointer ranges, clears new slots, and frees the old aligned allocation. The second helper ensures capacity, selects the target block and half-slot from the internal map index, stores two 32-bit values, and increments the element count.

IDA caller evidence ties the append helper to map/path scanning routines around `0x0050c790` and `0x0050d010`. Those callers enqueue candidate coordinates while checking neighboring map cells and collision/path costs.

## Reconstruction Notes

Do not reconstruct these helpers as manual project source unless later evidence proves the original used a custom container. The safer source-level reconstruction is a map pathfinding routine using `std::deque`, `std::queue`, or the project's equivalent point queue; the compiler/STL should regenerate the low-level map-growth and push support.

## Evidence

- IDA MCP reports real functions at `0x00514f70-0x00515100` and `0x00515110-0x005151a9`.
- IDA decompilation of `0x00515110` stores two 32-bit fields from the caller-supplied pair into a deque block.
- IDA xrefs to `0x00515110` all come from `MapPane` path/cell scanning functions at `0x0050c790` and `0x0050d010`.
- The helper bodies have MSVC deque-like allocation, segmented-map, and aligned-free patterns rather than domain-specific project logic.
- Live IDA MCP refresh on 2026-06-15 reconfirmed `sub_514F70` at `0x00514f70` size `0x190`, no function at `0x00515100`, `sub_515110` at `0x00515110` size `0x99`, no function at `0x005151a9`, and successor `sub_5151B0` at `0x005151b0`.
- The 2026-06-15 xref refresh found `0x00514f70` called only from the append helper at `0x00515132`, while `0x00515110` is called ten times from the two MapPane path-scan functions `0x0050c790` and `0x0050d010`.
- The 2026-06-15 callee refresh for `0x00514f70` reports allocator, `memmove`, `memset`, aligned-free/invalid-parameter, and growth-check helper callees; `0x00515110` calls `0x00514f70` and `operator new(0x10)`.
- The 2026-06-15 decompile refresh shows `0x00514f70` doubling/reallocating the segmented pointer map with 0x20-aligned large-allocation metadata and old-map free checks, and `0x00515110` storing two dwords from the caller pair into one of two 8-byte slots in a 16-byte block.
- Raw bytes from `0x00514f68` reconfirm five `0xcc` bytes before `0x00514f70`, sixteen `0xcc` bytes at `0x00515100-0x00515110`, and seven `0xcc` bytes at `0x005151a9-0x005151b0`.
