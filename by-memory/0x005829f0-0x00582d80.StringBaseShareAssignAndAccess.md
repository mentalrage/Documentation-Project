    const StringBase<char, mychar_traits<char> > &source)

    if (data == sourceData) {

    const RefCountedStringBufferHeader *sourceHeader =
        reinterpret_cast<const RefCountedStringBufferHeader *>(sourceData) - 1;

    if ((destinationHeader->refCount >= 0 || data == g_emptyAnsiString) &&
        sourceHeader->refCount >= 0) {
        ReleaseAnsiBuffer();
        InterlockedIncrement(
            const_cast<LONG *>(&sourceHeader->refCount));
        m_data = sourceData;
        return *this;

    const unsigned int visibleLength =
        static_cast<unsigned int>(strlen(sourceData));
    if (visibleLength < copyLength) {
        copyLength = visibleLength;

        destinationHeader->capacity < copyLength) {
        ReleaseAnsiBuffer();
        AllocateAnsiBuffer(copyLength);
        data = m_data;

    return *this;

## Behavior Notes

- All substantive helpers operate on the [UID:0001VQ][RefCountedStringBufferHeader](by-type/by-struct/RefCountedStringBufferHeader.md) layout: data pointer `-0x0c` is `refCount`, `-0x08` is `length`, and `-0x04` is `capacity`.
- `ShareOrCopyAnsiFromStringBase` and `ShareOrCopyWideFromStringBase` implement the same share-or-copy policy for ANSI and UTF-16 buffers. A source header with non-negative `refCount` is shareable; non-empty shareable sources are retained with `InterlockedIncrement`. A negative/non-shareable non-sentinel source is copied through `EnsureAnsiCapacity` or `EnsureWideCapacity` and `memmove`.
- `InitializeAnsiFromCountedBytes` and `InitializeWideFromRange` are construction/data-init helpers, not public conversion wrappers. They allocate through `AllocateAnsiBuffer` or `AllocateWideBuffer` and copy exactly the caller-specified byte/code-unit range.
- `InitializeEmptyAnsi` and `InitializeEmptyWide` are ten-byte sentinel initializers that store `g_emptyAnsiString` and `g_emptyWideString` directly.
- The two 54-byte destructor/release bodies contain compiler EH/security-cookie scaffolding around one release call each. The scaffolding is not source logic; the source-facing operation is `ReleaseAnsiBuffer()` or `ReleaseWideBuffer()`.
- `AssignAnsiFromStringBase` and `AssignWideFromStringBase` have assignment/operator-like behavior, but the accepted names avoid claiming symbol-proof of public `operator=` spelling. Both have a self guard, a share-retain fast path, and private-copy fallback.
- Empty-source assignment is a binary quirk: when the source pointer is the empty sentinel, the destination pointer is set to that sentinel and the old storage is not released in this helper body.
- Private-copy assignment clamps the copy count to the visible `strlen` / `wcslen` length before copying. When existing private destination capacity is sufficient, the helper copies bytes into the current buffer but does not rewrite the stored header length or terminator.
- `AssignWideLiteral` is not a ref-sharing path. It releases current wide storage, computes the raw literal length with `wcslen`, allocates through `AllocateWideBuffer`, and copies `count * sizeof(wchar_t)` bytes. The allocator writes the terminator.
- `GetWideAt` is a direct indexed wide accessor over `m_data[index]`.
- B007's [UID:00040Q][0x004f0380-0x004f03bb.LanguageManCopyLocalizedString](by-memory/0x004f0380-0x004f03bb.LanguageManCopyLocalizedString.md) report rechecks callee `0x00582560` as a UTF-16 StringBase assignment/copy path: it computes `wcslen`, allocates or grows through `0x00582e30`, copies through `memmove`, and returns the destination object. This reinforces the string-family ownership of the assignment callee while keeping the LanguageMan helper as a caller.
