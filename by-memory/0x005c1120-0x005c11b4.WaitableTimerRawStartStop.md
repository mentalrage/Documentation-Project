## Evidence

- IDA MCP `lookup_funcs` on 2026-05-31 reports `0x005c1120` and `0x005c1170` as not-a-function starts while confirming the neighboring modeled functions at `0x005c10a0`, `0x005c11c0`, and `0x005c1210`.
- Raw disassembly at `0x005c1120` shows a normal prologue, `ecx` used as `this`, a single stack argument read at `[ebp+8]`, and a `retn 4`.
- Raw disassembly at `0x005c1170` shows a separate `thiscall`-shaped body ending in plain `retn`.
- `0x005c1149` pushes callback address `0x005c11c0`; this explains the data xref from the raw gap into the IDA-modeled callback.
- [UID:0000WD][0x0041a280-0x0041a4a8.WideApiDispatchInit](by-memory/0x0041a280-0x0041a4a8.WideApiDispatchInit.md) writes `CreateEventW` to `dword_69BE3C` at `0x0041a30c`, so the helper-created `+0x28` handle is an event, not a worker thread.

## Generated Data Caveats

Current `source-3/simroot_v2/class_WaitableTimer.cpp` omits both raw helpers. Current generated metadata still names field `+0x28` as `m_hWorkerThread`, but the raw start helper creates it through `CreateEventW`, the callback waits/closes it, and the cancel/destructor paths close it as event-gate state.

These helpers should be restored as `WaitableTimer` methods or explicitly represented as raw helper bodies before source migration. Do not merge them into [UID:0000OT][TimerMgr](by-file/TimerMgr.md) just because they call `timeSetEvent`; their field access stays entirely inside the `WaitableTimer` layout.
