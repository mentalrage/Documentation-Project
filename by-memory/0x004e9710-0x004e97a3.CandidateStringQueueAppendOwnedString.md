## Evidence Notes

- IDA MCP confirms `0x004e9710` as a function of size `0x93`.
- IDA xrefs show direct callers from `InputMan::HandleWindowMessage` at `0x004e91a6` and `0x004e9234`.
- IDA decompilation shows a call to `CandidateStringQueue::ReserveAdditional` at `0x004e9726`, then slot allocation and move/reset of a 0x18-byte candidate string entry.
- IDA callers for [UID:0002MT][0x004e8860-0x004e89f2.CandidateStringQueueReserveAdditional](by-memory/0x004e8860-0x004e89f2.CandidateStringQueueReserveAdditional.md) include this function at `0x004e9726`, tying the append helper to the same deque map-growth implementation.
- The paired [UID:0001WO][CandidateStringDequeTemplate](by-type/by-template/CandidateStringDequeTemplate.md) evidence shows the destination container is a concrete MSVC/Dinkumware `std::deque<std::wstring>`-style instantiation, not a handwritten NexusTK queue class.
- Older Wave2 report notes already identify this as `CandidateStringQueue::AppendOwnedString`; current docs retain that as a generated behavior label while classifying the implementation as standard-library template support.

## Reconstruction Notes

- Rebuild `InputMan::HandleWindowMessage` as product code that creates/copies candidate wide strings and appends them to a candidate container.
- Do not migrate this helper as an original product method. The exact range is tracked in [UID:0000VN][-ignored](by-memory/-ignored.md) as STL template support.
