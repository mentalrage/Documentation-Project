## Evidence Notes

- Wave3 summaries identify both classes as small heap-array owners.
- IDA MCP on 2026-05-22 reports the allocation methods are called from both `MonsterImageLib::LoadMonsterTables` and `RidingImageLib::LoadRidingDefinitions`.
- The shared caller family means these helpers should not be treated as arbitrary monster-only spillover.
- IDA MCP on 2026-05-26 confirms [UID:0000TJ][RidingDefinitionGlobalTable](by-global/RidingDefinitionGlobalTable.md) at `0x0069b430` is a global instance of the 12-byte outer helper. The `dword_69B438` references in `LoadRidingDefinitions` are the object's `+0x08` entry pointer field, not a separate standalone global allocation.
- 2026-05-26 IDA `py_eval` recheck confirms modeled function starts at `0x00528950`, `0x005289d0`, `0x00528a70`, `0x00528af0`, `0x00528b10`, `0x00528b60`, `0x00528be0`, `0x00528c80`, and `0x00528d00`. No IDA names contain `MonsterImageLibTable`; only SEH labels include the address-derived helper starts, so current class names are documentation placeholders.
- 2026-05-28 IDA MCP recheck adds modeled helper starts at `0x00528930`, `0x00528d30`, and `0x00528d50`. Xrefs show `0x00528930` is called directly from `0x00419fb0`/`0x00419fd0` and passed as an element constructor callback from `0x004dac40`/`0x004dc420`; `0x00528d30` is passed as a constructor callback by `0x00528be0`; `0x00528d50` is a no-op callback passed by `0x00528b60`, `0x00528be0`, and `0x00528c80`.
- IDA xrefs confirm the allocation helpers at `0x005289d0` and `0x00528be0` each have four parser callers from `MonsterImageLib` and `RidingImageLib`, while fallback frame record `unk_66DEB0` is referenced by both frame-entry getters at `0x00528b10` and `0x00528d00`.
