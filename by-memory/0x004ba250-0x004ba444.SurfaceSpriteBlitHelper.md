## Behavior Detail

The source-facing signature remains inferred, but IDA's stack frame, caller setup, and GrafPort constructor evidence support a `thiscall` shape equivalent to:

```text
void GrafPort::BlitSurface(GrafPort *source,
                           const RectBounds *sourceRect,
                           const RectBounds *destinationRect,
                           int mode);
```

Observed paths:

- If destination byte `+0x94` is set, the helper uses software/composition immediately: update the source and destination surface metadata, copy source float `+0x90` to the destination when it is `<= 1.0`, call `dword_69B3E8` with destination in `ecx`, `source + 0x1c`, source/destination rectangles, mode, null palette, and `NULL` options, restore the saved destination float when appropriate, and clear cached/locked state fields at offsets `+0x20` and `+0x28` after optional vtable unlock calls.

- If destination byte `+0x94` is clear and `mode == 0`, it uses the same DirectDraw-surface vtable slot with flag `0x10`, `DDBLTFAST_WAIT`.
- For other modes on a DirectDraw-backed destination, it falls back to the same metadata/update, alpha borrow/restore, `dword_69B3E8` call with `NULL` options, and `EndPaint` sequence. Layer and effect callers pass broader pane draw-mode bytes such as `sourcePane + 0xb5`, so only modes `0` and `1` should be named precisely here.
