## Behavior

The routine blends two RGB555 pixels without touching global state or calling other functions. It keeps the green channel separate with mask `0x03e0`, keeps red/blue together with mask `0x7c1f`, multiplies the first color by the supplied weight, multiplies the second color by `32 - weight`, shifts both accumulated channel groups right by five, masks them back to RGB555 lanes, and ORs the result together.

This is handwritten/source-owned render math rather than CRT/compiler glue. Final source keeps it as a small free helper under the `SoftwareBlend16` render grouping. `BlendRgb555` is an inferred source-facing name rather than a proven original symbol, and the public/header placement is still unresolved, but those uncertainties are score caps only. Current reconstruction rules allow first-draft formal C++ because the target is reconstructable, has a nonblank SoftwareBlend16 emitter, and clears the active code-entry score gate.

The formal signature uses `unsigned short __cdecl BlendRgb555(unsigned short firstPixel, unsigned short secondPixel, unsigned char firstWeight32)`. Hex-Rays reports an unsigned integer return, but every arithmetic lane is masked back to RGB555 and representative compatibility-render callers store the return value into 16-bit destination pixels. The first argument is weighted by `firstWeight32`; the second is weighted by the byte-wrapped inverse `static_cast<unsigned char>(32 - firstWeight32)`, matching the binary's `0x20 - weight` calculation.
