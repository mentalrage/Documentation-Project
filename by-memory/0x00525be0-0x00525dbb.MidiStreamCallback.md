## Signature

IDA decompiles the body as:

```c
signed int __stdcall sub_525BE0(int hMidi, int message, int instance, DWORD *header, int param2)
```

The stack cleanup is `retn 14h`, matching the five-argument WinMM callback shape. The first, third, and fifth arguments are not materially used by this body; the message id and MIDI header/event pointer drive the logic.

## Behavior

This is the callback passed to `midiStreamOpen` by [UID:0001CE][0x00525920-0x00525b0d.MidiStreamOpenAndPrimeBuffers](by-memory/0x00525920-0x00525b0d.MidiStreamOpenAndPrimeBuffers.md).

Live IDA MCP decompilation and disassembly show two message paths:

| Message | Address path | Behavior |
| --- | --- | --- |
| `0x3ca` / `970` | `0x00525bf1-0x00525c6f` | Handles MIDI event callback data. It reads the current event dword from `header->lpData + header->dwBytesRecorded + 8`, filters for controller-change status `0xb0` and controller `7` volume events, updates the per-channel volume table at `0x0069b5d0 + channel * 4`, and, when playback is active, sends a scaled controller-7 message through `midiOutShortMsg(hms, ...)`. |
| `0x3c9` / `969` | `0x00525c72-0x00525db8` | Handles buffer-return/completion. It ignores callbacks once state `0x0069b508` is already idle/done (`200`), increments the pending-return counter, handles stop/reset states `300` and `100` when both prepared buffers have returned, optionally calls reset helper [UID:0001CF][0x00525b10-0x0052664b.MidiPlayerAndWinMMHelpers](by-memory/0x00525b10-0x0052664b.MidiPlayerAndWinMMHelpers.md), signals `hObject`, and otherwise refills/requeues the active MIDI stream buffer. |

On refill, the callback clears the current `MIDIHDR` bookkeeping fields, calls [UID:00023C][0x005271b0-0x005277bb.MidiSMFLoadAndStreamFillHelpers](by-memory/0x005271b0-0x005277bb.MidiSMFLoadAndStreamFillHelpers.md) with the static MIDI document state and target buffer, writes `dwBytesRecorded`, submits the header with `midiStreamOut`, rotates the two-buffer index modulo 2, and decrements the pending-return counter. Return `0xffffff99` from the fill helper marks end-of-stream: the callback sets the end marker at `0x0069b86c`, moves state `0x0069b508` to `300`, and waits for both buffers to return. Other non-zero fill or stream-output failures release document resources through [UID:0001CI][0x005270e0-0x005271a3.MidiDocumentRelease](by-memory/0x005270e0-0x005271a3.MidiDocumentRelease.md).

The volume path scales controller value by `0x0069b524 / 1000`, places the scaled value in the high data byte, preserves the channel nibble, and emits controller `7` (`0x7b0 | channel | scaled << 16`) through `midiOutShortMsg`.

## Reconstruction Notes

Keep this in `audio/MidiPlayer.cpp` or a private WinMM MIDI support block. It is not generic callback infrastructure and should not be migrated to `SoundManager.cpp`.

Keep this paired with [UID:0001CE][0x00525920-0x00525b0d.MidiStreamOpenAndPrimeBuffers](by-memory/0x00525920-0x00525b0d.MidiStreamOpenAndPrimeBuffers.md): that helper installs the callback and primes the first buffers; this callback handles asynchronous buffer returns, refills, reset completion, and live volume messages.

C++ remains blank because final source still needs stable callback message constants, state-global names, stream-buffer field names, and a better final name for the state values `100`, `200`, and `300`.
