## Behavior

This is the callback passed to `midiStreamOpen` by [UID:0001CE][0x00525920-0x00525b0d.MidiStreamOpenAndPrimeBuffers](by-memory/0x00525920-0x00525b0d.MidiStreamOpenAndPrimeBuffers.md) and by raw helper [UID:00041K][0x00525f40-0x0052609a.MidiPlayerRawVolumeAndStreamLocalHelpers](by-memory/0x00525f40-0x0052609a.MidiPlayerRawVolumeAndStreamLocalHelpers.md)'s `OpenMidiStreamCallbackOnly`.

Live IDA MCP decompilation and disassembly show two message paths:

| Message | Address path | Behavior |
| --- | --- | --- |
| `MOM_POSITIONCB` / `0x3ca` / `970` | `0x00525bf1-0x00525c6f` | Handles MIDI event callback data. It reads the current event dword from `header->lpData + header->dwBytesRecorded + 8`, filters for controller-change status `0xb0` and controller `7` volume events, updates the per-channel volume table at `0x0069b5d0 + channel * 4`, and, when playback is active, sends a scaled controller-7 message through `midiOutShortMsg(hms, ...)`. |
| `MOM_DONE` / `0x3c9` / `969` | `0x00525c72-0x00525db8` | Handles buffer-return/completion. It ignores callbacks once state `0x0069b508` is already idle/done (`200`), increments the pending-return counter, handles stop/reset states `300` and `100` when both prepared buffers have returned, optionally calls reset helper [UID:00041O][0x00526460-0x00526569.MidiPlayerResetStream](by-memory/0x00526460-0x00526569.MidiPlayerResetStream.md), signals `hObject`, and otherwise refills/requeues the active MIDI stream buffer. |

On refill, the callback treats the active `MIDIHDR` storage as the accepted `MidiStreamWriteContext` base: `lpData` at `+0x00` is the target stream buffer pointer, while writer fields at `+0x40/+0x44/+0x48/+0x4c/+0x50` are cleared for write offset, write limit, bytes written, last event tick, and output-full state. It calls [UID:0002C6][0x005271b0-0x005273a0.MidiStreamBufferFillHelper](by-memory/0x005271b0-0x005273a0.MidiStreamBufferFillHelper.md) with the static MIDI document state, `resetState == FALSE`, the active stream context, and `g_midiAllowEndReplay`; copies `stream->bytesWritten` to `MIDIHDR::dwBytesRecorded`; submits the header with `midiStreamOut(g_hMidiStream, header, sizeof(MIDIHDR))`; rotates the two-buffer index modulo 2; and decrements the pending-return counter. Return `0xffffff99` (`MIDI_FILL_END_OF_STREAM`, `-103`) from the fill helper marks end-of-stream: the callback sets the end marker at `0x0069b86c`, moves state `0x0069b508` to `300`, and waits for both buffers to return. Other non-zero fill or stream-output failures release document resources through [UID:0001CI][0x005270e0-0x005271a3.MidiDocumentRelease](by-memory/0x005270e0-0x005271a3.MidiDocumentRelease.md). `MIDI_FILL_OUTPUT_FULL` (`-104`) is replayed inside the fill helper by preserving `g_midiPendingEvent`.

The volume path scales controller value by `0x0069b524 / 1000`, places the scaled value in the high data byte, preserves the channel nibble, and emits controller `7` (`0x7b0 | channel | scaled << 16`) through `midiOutShortMsg`.

[UID:0002BV][0x005269f0-0x00526ba8.MidiStreamEventEncoder](by-memory/0x005269f0-0x00526ba8.MidiStreamEventEncoder.md) now names the corresponding stream-encoder tag as the controller-volume callback marker: channel controller `0xb0`, controller `7`, and packed event OR `0x40000000`. This callback consumes that tagged event to update the per-channel volume table before forwarding scaled volume to WinMM.
