## Interpretation

These six functions are the destructor entries used by secondary and tertiary vtable views in the reusable input-pane inheritance layout. The incoming `this` pointer is a subobject pointer at `+0xa0` or `+0xa4`; the thunk subtracts that offset and tail-jumps to the real scalar deleting destructor. No cleanup policy, UI behavior, or key-input behavior lives in these wrappers.

For source reconstruction, express this as normal virtual destructors on the C++ classes and let the compiler produce adjustor thunks as needed. Do not add explicit `AdjustorThunkDestructor` member functions to reconstructed project source.

## Evidence

- IDA MCP `lookup_funcs` on 2026-05-26 reports each thunk as an `0xb`-byte function. `0x004f2dd0` is the preceding `0x89`-byte non-deleting destructor, `0x004f2e9b-0x004f2e9f` is not a function, and `0x004f2ea0` starts the shared scalar deleting destructor.
- IDA MCP `disasm` shows every thunk is exactly `sub ecx, <0xa0 or 0xa4>` followed by a tail `jmp` to the matching scalar deleting destructor.
- IDA MCP `xrefs_to` shows only vtable data refs for the thunk starts, plus code refs from the thunk tail jumps into destructor targets.
- `0x004f2e59` is referenced by vtables `0x0061caa8`, `0x0061cb34`, `0x0061ccd8`, `0x0061cd64`, and `0x0061cdf0`.
- `0x004f2e64` is referenced by vtables `0x0061cad8`, `0x0061cb64`, `0x0061cd08`, `0x0061cd94`, and `0x0061ce20`.
- `0x004f2e6f`, `0x004f2e7a`, `0x004f2e85`, and `0x004f2e90` are referenced by `CharInputPane` and `ConfirmInputPane` secondary/tertiary vtables at `0x0061cbc0`, `0x0061cbf0`, `0x0061cc4c`, and `0x0061cc7c`.

## Data Caution

Current `simroot_v2` metadata propagates these thunk addresses into generated class method inventories and, for some classes, rewrites them as source-like destructor wrappers with incorrect member-field reasoning. Treat the IDA disassembly and vtable xrefs above as the authoritative interpretation.
