# 0x0054c200-0x0054caa9 Message Dialog Packet Dispatcher And Wrappers

## Status

- Disposition: reconstructable NexusTK project code.
- Entity kind: packet dispatcher and dialog factory wrapper cluster.
- Current generated owner: `Motion::HandleDialogPacket` in `source-3/simroot_v2/class_Motion.cpp`.
- Corrected source owner: [UID:0000LA][MessageDialogs](by-file/MessageDialogs.md), not [UID:0000LL][Motion](by-file/Motion.md).
- Confidence: strong for `MessageDialogs` ownership and function boundaries.

## Covered Range

| Range | Working name | Notes |
| --- | --- | --- |
| `0x0054c200-0x0054c511` | `HandleDialogPacket_54C200` | Decodes `packet[1]`; bit `0x10` selects larger-layout dialog families and the low nibble selects message/menu-question/text/head/proxy dialog construction. |
| `0x0054c570-0x0054caa9` | dialog allocation wrappers | Small SEH-protected allocation wrappers that allocate dialog objects and call specific constructors such as `MessageDialog`, `MessageDialogLarger`, `MenuQuestionDialog`, `MenuQuestionDialogLarger`, `TextDialog`, `NexonclubProxyDialog`, and `HeadSelectDialog`. |

Internal bytes between the dispatcher and wrappers, and between individual wrappers, are compiler/linker alignment padding inside this source-local helper island. The following boundary padding is tracked separately in [UID:0000VN][-ignored](by-memory/-ignored.md).

## Behavior

The dispatcher receives a dialog packet payload pointer. It reads `packet[1]` through the narrow character traits helper, tests bit `0x10`, and uses the low nibble as a dispatch selector. Direct constructor paths allocate `0x278` bytes for the message/menu-question dialog family, then pass `packet + 2` and a layout/text-mode flag to the selected constructor.

The second half of the island is a set of allocation wrappers. Some are reached from the dispatcher, while others currently have no direct code callers in IDA but are layout-equivalent helper wrappers for the same dialog family. These wrappers are still project source behavior because they instantiate dialog classes and are not CRT/STL/compiler runtime support.

## Evidence

- 2026-05-28 IDA MCP `py_eval` reports `0x0054c1f1-0x0054c200` as `0xcc` alignment, then functions from `0x0054c200` through `0x0054caa9`, followed by `0x0054caa9-0x0054cab0` alignment.
- IDA MCP `analyze_funcs 0x0054c200` decompiles the main dispatcher as a packet-byte selector that allocates dialog objects and calls `0x0054ce10`, `0x0054db90`, `0x0054e920`, `0x0054fb30`, wrapper functions, and the text/head/proxy dialog constructors.
- IDA caller evidence for `0x0054c200` shows callers at `0x00507e2e` and `0x0051287f`, matching inbound packet/dialog-open paths rather than motion animation.
- Existing data-issue notes already classify current `Motion::HandleDialogPacket` ownership as generated-owner pollution; this page makes the range explicit in by-memory coverage.

## Source-Structure Decision

Keep this range with [UID:0000LA][MessageDialogs](by-file/MessageDialogs.md). It is the packet entry point and allocation wrapper island for the NPC/message/menu-question/text/head dialog flow. Do not migrate it into [UID:0000LL][Motion](by-file/Motion.md) despite the current generated file owner.
