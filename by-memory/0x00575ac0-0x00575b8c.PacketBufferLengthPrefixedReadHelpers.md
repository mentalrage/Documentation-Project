# 0x00575ac0-0x00575b8c PacketBuffer Length-Prefixed Read Helpers

## Status

- Disposition: reconstructable NexusTK project code
- Entity kind: packet helper function pair
- Current generated owner: recovered global helpers
- Likely source module: [UID:0000M8][PacketBuffer](by-file/PacketBuffer.md)
- Confidence: strong for behavior and PacketBuffer ownership; medium for final source-facing names.

## Covered Range

This file documents two adjacent two-byte length-prefixed packet readers found while splitting the former `0x00575abb-0x00575cb0` UNKNOWN row. IDA MCP confirms the first function is not referenced by direct code xrefs, while the second is called from `MainMenuPane` and `MapPane` packet handlers.

| Range | Current name | Notes |
| --- | --- | --- |
| `0x00575ac0-0x00575b42` | `sub_575AC0` | Reads a big-endian 16-bit length, copies that many bytes from `base + *cursor + offset`, advances the cursor, constructs/copies into an `LObject`-style string object, and destroys the temporary. |
| `0x00575b50-0x00575b8c` | `sub_575B50` | Reads a big-endian 16-bit length, copies the byte span into caller-provided storage through `sub_582A50`, advances the cursor, and returns the storage pointer. |

Internal `0xCC` padding at `0x00575b42-0x00575b50` is alignment between the two helpers, not source logic.

## Evidence

- 2026-05-28 IDA MCP disassembly reports `sub_575AC0` as `0x00575ac0-0x00575b42` and `sub_575B50` as `0x00575b50-0x00575b8c`.
- `sub_575AC0` uses the same big-endian two-byte length decode as `sub_575B50`, then calls `sub_582A50`, `sub_582830`, and `sub_582B30` around a temporary string object.
- `sub_575B50` has direct IDA code refs at `0x004f74ee` and `0x00508bec`, both packet-handler paths that parse opcode/case `91` payload text into client state.
- `simroot_v2/class_MapPane.cpp` also declares and calls `sub_575B50`, but that generated name is only a lead. IDA confirms the exact boundary, callers, and helper behavior.
