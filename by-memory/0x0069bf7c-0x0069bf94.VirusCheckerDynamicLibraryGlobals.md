# 0x0069bf7c-0x0069bf94 VirusCheckerDynamicLibraryGlobals

## Summary

- Address range: `0x0069bf7c-0x0069bf94`.
- Entity kind: global-data cluster.
- Rebuild handling: `source-declared/generated-binary`.
- Disposition: reconstructable VirusChecker dynamic-library handles and function pointers.
- Confidence: strong for addresses, loader/cleanup behavior, and API roles.

## Slots

All six dwords are initialized as `0xffffffff` in `.data`; the loader turns them into runtime handles/pointers and cleanup paths clear them.

## Evidence

- IDA MCP `py_eval` on 2026-05-28 reports all six dwords initialized to `0xffffffff` with data xrefs from the VirusChecker constructor/destructor/load/scan helpers.
- Decompilation of `0x005c05a0` loads `V3PRO32E.DLL`, resolves `AhnExCheckFile` and `AhnExGetVirusName`, loads `V3PCTRL.DLL`, then resolves `V3PCtrl_EnumProcesses` and `V3PCtrl_EnumModules`.
- Decompilation of `0x005c07b0` calls the process enumeration pointer, calls `AhnExCheckFile`, and uses the `AhnExGetVirusName` pointer for detection reporting.
- Decompilation of `0x005c04e0` and scalar cleanup at `0x005c0ec0` frees the module handles and clears the function-pointer globals.
- Read-only string evidence for the DLL/export names is documented in [UID:00026Z][0x0063104c-0x00631184.VideoVirusReadOnlyData](by-memory/0x0063104c-0x00631184.VideoVirusReadOnlyData.md).

## Reconstruction Notes

These are source-declared static globals or static class/module variables owned by `VirusChecker`. The rebuilt project should declare typed `HMODULE` handles and function-pointer typedefs, then resolve them through `LoadLibraryW`/`GetProcAddress`; it should not preserve generated names such as `dword_69BF80` or fixed addresses.

This range ends immediately before [UID:0001Q3][0x0069bf94-0x0069bf98.g_pVirusChecker](by-memory/0x0069bf94-0x0069bf98.g_pVirusChecker.md) `g_pVirusChecker` at `0x0069bf94`, so the singleton object pointer is intentionally documented separately.
