# 0x0054c160-0x0054c1f1 DequeClear

## Status

- Disposition: non-emitting MSVC/Dinkumware `std::deque<int>` cleanup/toolchain support.
- Entity kind: lowered storage cleanup used by PrimeNumberGenerator construction, cleanup, and destruction paths; historical `Deque::Clear` is not a source method.
- Documentation grouping: [UID:00003P][Deque](by-class/Deque.md), now false/non-emitting; [UID:0000IR][Deque](by-file/Deque.md) has projected path `NONE`.
- Confidence: very strong for boundary, field offsets, storage-free behavior, Prime call sites, and standard-library source cause.

## Behavior

`sub_54C160` clears the Deque block-map storage without interpreting or releasing the payload values:

- reads `count` from `+0x10` and decrements it to zero;
- resets `frontIndex` at `+0x0c` only when the count drain reaches the final element;
- reads `blockCount` from `+0x08` and walks block-map slots in reverse order;
- for each non-null block pointer in the map at `+0x04`, frees the 16-byte block through the shared `sub_5C7526` free wrapper callsite;
- reloads the block map pointer from `+0x04`;
- when the block map allocation byte size `4 * blockCount` is at least `0x1000`, validates the MSVC aligned-allocation back-pointer at `map[-1]` and branches to `__invalid_parameter_noinfo_noreturn` on a bad header;
- frees the block-map allocation base through `sub_5C7526`;
- clears `blockCount` at `+0x08` and `blockMap` at `+0x04`;
- leaves the auxiliary `+0x00` owned pointer/storage slot untouched.

The field offsets match [UID:0001U2][DequeLayout](by-type/by-struct/DequeLayout.md): `+0x04` block map, `+0x08` block count, `+0x0c` front index, and `+0x10` count. This is the non-owning cleanup variant: it frees container storage but does not release ref-counted or heap-owned entry payloads.
