## IDA MCP Evidence

- `lookup_funcs` does not report functions at sampled addresses from `0x004f50b0` through `0x004f5240`; current IDA has these bytes as unpromoted code.
- Raw disassembly at `0x004f50b0` starts with a standard frame, calls `0x00458500` for image-state setup, opens the input path through `dword_69BE14(..., "rb")`, reads a 4-byte size, allocates and reads that many bytes, computes `word_66DA94 * word_66DA98`, calls the decompressor at `0x00414390`, stores decoded output at `this + 0xfc`, initializes rect/state at `+0x108` and `+0x11c`, and then reads/loads the palette.
- Raw disassembly near `0x004f5210` shows the file-close tail, the shared epilogue ending with `ret 4` at `0x004f521b`, followed by a second helper at `0x004f5220`.
- The second helper pushes `dword_69B36C`, passes `this + 0x108` into virtual slot `+0x30`, then calls virtual slot `+0x3c`.
- `xrefs_to 0x004f50b0` and `xrefs_to 0x004f5210` are empty in the current IDB; this is a promoted-boundary issue, not evidence that the bytes are padding.
