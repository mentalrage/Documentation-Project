## Storage And Lifetime

This four-byte global stores the process-wide EPF/EPD image/layout registry pointer. The object it points to is anchored by [UID:0001US][ImageLibLayout](by-type/by-struct/ImageLibLayout.md) and [UID:0001XR][ImageLibVtable](by-type/by-vtable/ImageLibVtable.md). It owns a [UID:000079][List](by-class/List.md) at offset `+0x0c`; that list contains 44-byte [UID:0001VT][ResourceLayoutNameRecord](by-type/by-struct/ResourceLayoutNameRecord.md) rows.

Observed writes:

- `0x004cffef`: `ImageLib::ImageLib` stores `this` into `dword_67A744`.
- `0x004cfff6`: constructor nulls the global if the adjusted object pointer path is null.
- `0x004d00fa`: `ImageLib` destructor cleanup path clears or updates the same storage.
- `0x004e5b90`: singleton-clear helper writes zero to the same storage.
- `0x004e652c`: scalar deleting destructor cleanup path clears the same storage.

IDA MCP xrefs show many additional data reads from UI panes, image libraries, and resource helpers. Those reads are consumers, not owners.

## 2026-06-05 IDA Evidence

Live IDA MCP confirms `0x0067a744` is named `dword_67A744`, is not a function, and is a four-byte zero-initialized `.data` slot bounded by neighboring zeroed dwords from `0x0067a738` through `0x0067a758`. The slot has 231 data xrefs.

Owner writes and clears:

- `0x004cffef`: `ImageLib::ImageLib` stores `this` into `dword_67A744`.
- `0x004cfff6`: the constructor null-fallback clears `dword_67A744`.
- `0x004d00fa`: ordinary destructor cleanup clears `dword_67A744`.
- `0x004e5b90`: small singleton-clear helper writes zero to `dword_67A744`.
- `0x004e652c`: scalar deleting destructor cleanup clears `dword_67A744`.

The refreshed decompilation evidence shows the constructor at `0x004cffb0-0x004d006f` installs `off_61B654`, initializes list-related fields, allocates a 20-byte helper object, and constructs the resource-layout list with 44-byte rows and capacity 10. The ordinary destructor at `0x004d0070-0x004d011b` and scalar deleting destructor at `0x004e64a0-0x004e6572` iterate the list count at `+0x0c`, free row payloads at `+0x28`, destroy the list object, clear this global, and run base teardown.

Consumer reads include fitting-room UI/resource paths such as `0x0041f2fb` in `FittingRoomListPane::OnPaint`, plus broad image, minimap, and render helpers. These consumers do not own the global.

## Ownership Decision

The global belongs with [UID:0000K2][ImageLib](by-file/ImageLib.md), not with a pane or asset-specific image library. The recovered `ResourceLayoutTable` methods use this pointer as their object, but `ImageLib::ImageLib` owns initialization and `ImageLib` destruction owns shutdown.

The registry store is not a separate proven class. IDA MCP follow-up shows `ImageLib::ImageLib` constructs it with `List::List(44, 10)`, so `ResourceLayoutStore` should remain a provisional alias over the generic `List`.

Keep the final C++ type open until the `ImageLib` / `ResourceLayoutTable` class boundary is resolved. The best declaration hypothesis remains an external `ImageLib` pointer named `g_pEPFLib`, with a note that callers currently use a `ResourceLayoutTable`-style API on the same object.
