## Evidence

- 2026-06-01 IDA MCP `py_eval` function inventory confirms promoted function starts at `0x00584d80`, `0x00584df0`, `0x00584e40`, and `0x00584e60`, with final padding `0x00584e9e-0x00584ea0` as two `0xcc` bytes.
- The same raw-byte inventory proves `0x00584db1-0x00584df0` and `0x00584dfb-0x00584e40` are not pure padding. They contain three complete helper bodies at `0x00584dc0`, `0x00584e00`, and `0x00584e30` separated by `0xcc` alignment bytes.
- `decompile 0x00584d80` initializes the base through `0x004f4a80`, stores `this[1]=text`, `this[2]=length`, writes the `StringIter` vtable, and sets `this[3]=0`.
- Raw bytes for `0x00584dc0` show the same constructor shape with an additional `this[3]=startPosition` write.
- `decompile 0x00584e40` reads `position=this[3]`, returns zero when `position >= length`, otherwise returns `*(uint16_t *)(text + 2*position)` and increments position.
- `decompile 0x00584e60` writes the `StringIter` vtable, calls base destruction through `0x004f4a90`, and conditionally frees through `0x004f4ac0` when the scalar-deleting flag requests it.
- `callers 0x00584d80`, `0x00584df0`, and `0x00584e40` are concentrated in `0x004ba8b0`, `0x004ba9a0`, `0x004bab70`, and `0x005948a0`, matching the documented text parsing/render helper use.
- `callees 0x00584d80` reports only the base constructor `0x004f4a80`; `callees 0x00584e40` is empty, supporting a leaf iterator-next method.
- The object layout is 16 bytes: vtable/base at `+0x00`, text pointer at `+0x04`, length at `+0x08`, and current position at `+0x0c`.
