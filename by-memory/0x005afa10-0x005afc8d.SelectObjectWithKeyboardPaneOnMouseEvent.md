## Behavior

The method handles two mouse-event subtypes from `event + 4`:

| Event subtype | Behavior |
| --- | --- |
| `1` | Treats `event+8/event+0x0c` as mouse coordinates, translates them from this pane's coordinate origin into active-map coordinates, calls [UID:0001AU][0x00506ce0-0x00506d15.GeneratedBackPaneHitTestMapPane](by-memory/0x00506ce0-0x00506d15.GeneratedBackPaneHitTestMapPane.md), and updates the current `dword_69BF28` selected target. When the hit object differs from the previous target, it clears the old highlight, highlights the new object, stores the new object's `+0xfc` id, and may immediately confirm/dismiss if the config byte at `dword_67A7C8 + 0x28de5a` allows it and a previous target existed. When the hit object equals the current target, the same config gate decides whether a click confirms the current selection. If no object is hit but the point remains inside the map rectangle, the method can confirm the existing target through the same cleanup path. |
| `2` | Treats the event as a confirm/click path over the active map rectangle. It resolves `dword_69BF28`, checks whether the translated point lies inside the active map rectangle, clears the current target highlight, resets local-player/player-state field `dword_67A748 + 0x210`, calls `sub_50B1B0(dword_67A764, target)` to interact with the target, dismisses this selector through `sub_469180(dword_67A74C, owner)`, and runs the shared post-confirm cleanup. |

The shared post-confirm cleanup clears `dword_67A748 + 0x210` again, then, if `dword_67ADE0 + 0x111` is set, clears `dword_67A748 + 0x3eb4` and calls virtual slot `+0x48` on `dword_67ADD8`. Existing global docs identify those latter globals as chat UI singleton slots; the exact reason target selection resets that state remains an open UI-integration naming question.
