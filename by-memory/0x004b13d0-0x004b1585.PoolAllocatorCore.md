## Allocator State Model

| Offset | Field hypothesis | Established transitions |
| --- | --- | --- |
| `+0x00` | `blockSize` | Written by the constructor/init path and used by `Allocate` when requesting a new chunk. |
| `+0x04` | `blocksPerChunk` | Written by the constructor/init path and passed with `blockSize` to the chunk allocation helper. |
| `+0x08` | `chunkList` | Cleared by construction, prepended by [UID:0001F4][0x00549bd0-0x00549bf1.PoolAllocatorChunkHelper](by-memory/0x00549bd0-0x00549bf1.PoolAllocatorChunkHelper.md), passed to [UID:00023L][0x00549c00-0x00549c18.PoolAllocatorFreeChunkList](by-memory/0x00549c00-0x00549c18.PoolAllocatorFreeChunkList.md), then cleared by destruction. |
| `+0x0c` | `freeList` | Cleared by construction, refilled by `Allocate` when a chunk is added, popped by `Allocate`, pushed by the free-list return helper, and cleared by destruction. |
| `+0x10` | `CRITICAL_SECTION` | Initialized by construction, held during allocation/free/destroy list mutation, and deleted by destruction. |

## Ownership Notes

This island should be migrated with the fixed-block allocator, not treated as UI/object-list code. `ThreadSafeNodeList` remains a useful behavior alias for `0x004b14c0`, but the string-pool xrefs make `PoolAllocator` the stronger file-level owner for the whole method family.

The eight string pools are confirmed users, not the full allocator inventory. The extra constructor/destructor wrappers include object-pane, `Motion`, and `UserPane` pools, so final source migration should keep allocator mechanics separate from concrete per-class pool globals.

The attached helper pages now cover both non-contiguous chunk operations. Keep the local island page focused on constructor/allocate/free/destroy state transitions, and keep concrete chunk allocation/free loop details in the helper pages unless final source evidence proves they were inline or method-local.
