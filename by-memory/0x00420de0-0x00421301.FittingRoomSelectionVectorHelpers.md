# 0x00420de0-0x00421301 FittingRoom Selection Vector Helpers

## Status

- Address range: `0x00420de0-0x00421301`
- Entity kind: helper island / container helpers
- Proposed owner: mixed. The 180-byte item-entry vector insert/copy helpers are fitting-room item-state/list helpers under [UID:0000JE][FittingRoom](by-file/FittingRoom.md); the pointer-vector and formatting wrappers have non-fitting-room callers and should stay shared/provisional.

- Confidence: strong for function boundaries, caller map, element sizes, and fitting-room-owned entry insertion role; medium for final source-level helper names and exact template placement.

## Evidence

- IDA MCP `lookup_funcs` reports exact function records: `0x00420de0` size `0x10a`, `0x00420ef0` size `0x253`, `0x00421150` size `0xdb`, `0x00421230` size `0x2d`, `0x00421260` size `0x30`, and `0x00421290` size `0x71`. `0x00421301` is not a function; byte review shows the `0x00421290` return at `0x00421300` followed by `0xcc` padding, with the next function beginning at `0x00421310`.
- `xrefs_to 0x00420de0` reports calls at `0x0041fef1`, `0x00422d31`, and `0x004e020d`. `0x0041fef1` is list-pane input selection handling; `0x00422d31` is fitting-room item-state/category loading; `0x004e020d` is outside the fitting-room neighborhood.
- `xrefs_to 0x00420ef0` reports one caller, `0x00420191` inside [UID:0002DN][0x0041fcd0-0x004207ce.FittingRoomListPaneOnInputEvent](by-memory/0x0041fcd0-0x004207ce.FittingRoomListPaneOnInputEvent.md). That makes the 180-byte entry insert helper fitting-room-list specific.
- `xrefs_to 0x00421150` reports only the three internal calls from `0x00420ef0` at `0x0042105e`, `0x0042106b`, and `0x00421078`.
- `decompile 0x00420ef0` divides vector byte distances by `180`, allocates `180 * newCapacity`, copies `0xa0` bytes from source offset `+4`, copies a word at source offset `+0xa4`, calls `0x00421290` for the nested pointer vector at source offset `+0xa8`, calls `0x00421150` to move/copy existing ranges, calls `0x00421380` while releasing old entries, and uses MSVC aligned-allocation validation before freeing old storage.
- `decompile 0x00421150` copies/moves 180-byte entries in a loop, transfers nested vector fields around offsets `+0xa8/+0xac/+0xb0`, and zeros the source nested-vector fields after transfer. This is move-construction behavior for the fitting-room item-entry vector, not a generic byte copy.
- `decompile 0x00421230` and `0x00421260` prove the fixed capacities: `0x20` and `0x80` wide characters respectively. `xrefs_to 0x00421230` includes fitting-room paint at `0x0041f9e7` / `0x0041f9fc` and non-fitting-room UI formatting callers at `0x0057fb94` and `0x005800de`; `xrefs_to 0x00421260` reports fitting-room paint at `0x0041f89b`.
- `decompile 0x00421290` zeroes a three-pointer destination vector, calculates `((*srcEnd - *srcBegin) >> 2)`, allocates with `0x00421520`, copies the pointer span through `memmove_0`, and updates the destination end. Callers include `0x00420179`, `0x00421047`, `0x004224b7`, `0x004226fe`, `0x00422d65`, and `0x005c2c7b`.
- Narrow caller checks show `0x004226d0` copies a category pointer vector through `0x00421290`, indexes by a short argument, and releases the temporary vector through `0x00423810`; `0x00422470` iterates item-state/category entries and copies nested vectors through `0x00421290`; `0x005c2ac0` uses the same pointer-vector copy helper outside fitting-room.
