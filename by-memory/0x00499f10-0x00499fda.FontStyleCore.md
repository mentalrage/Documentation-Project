## Constructor Behavior

The constructor initializes a 0x20-byte style object:

- `m_rules._First`, `m_rules._Last`, and `m_rules._End` are set to null by the default construction of the vector-style rule collection.
- `m_enabled` at `+0x00` is set to `1`, source-expressed as `bool` value `true`.
- `m_parentOpacity` at `+0x04` and `m_textOpacity` at `+0x08` are set to `0.2f`; the `+0x08` field is the active text opacity used by the HelpPane text-part path, while `+0x04` remains the paired parent/pane opacity scalar.
- `m_foregroundColor` at `+0x0c` and `m_backgroundColor` at `+0x10` are set to `1` and `0x80`.
- Padding bytes are not assigned source-visible values; the `+0x09..+0x0b` rule gap is natural alignment before dword `m_alignment`, not an explicit source member.

## Rule Lookup Behavior

The `0x00499f60` helper computes the current rule count from the vector triplet at offsets `+0x14/+0x18/+0x1c` only for the bounds check. When the requested index is in range, it copies the selected 16-byte rule record into the caller-provided output buffer. Out-of-range indexes leave the output unchanged.

[UID:0004L8][0x0049a080-0x0049a298.StaticTextControlPane2SimpleHelpTextPartPaneOnPaint](by-memory/0x0049a080-0x0049a298.StaticTextControlPane2SimpleHelpTextPartPaneOnPaint.md) supplies the second exact consumer family: it initializes fallback rule fields once, requests successive unsigned line indexes, and intentionally relies on out-of-range `GetRule` preserving the current fallback or previous record before [UID:0004LB][0x0049a330-0x0049a403.StaticTextControlPane2SimpleHelpTextPartPaneDrawTextLine](by-memory/0x0049a330-0x0049a403.StaticTextControlPane2SimpleHelpTextPartPaneDrawTextLine.md) consumes the four semantic fields. This corroborates the void side-effect signature and rejects count/bool/pointer return models without changing this page's score or formal C++.

Source-facing signature:

```cpp
void FontStyle::GetRule(unsigned int index, FontStyleRule *outRule) const;
```

The old count-returning interpretation is rejected. Direct instruction behavior explains the ambiguity: the out-of-range path leaves a count-like value in `eax`, while the in-range path changes `eax` to the output-buffer pointer before the 16-byte copy. Known callers at `0x004c6723` and `0x004c67b3` ignore the return register and use only the side effect. Do not model this as `unsigned int GetRule(...)`, `bool GetRule(...)`, `FontStyleRule *GetRule(...)`, or `operator[]`.

## Configure Behavior

`Configure(textColor, secondaryColor, effect, alignment)` builds a 16-byte `FontStyleRule` and appends it to the vector triplet at object offset `+0x14`:

- `m_textColor` is stored at rule offset `+0x00`.
- `m_secondaryColor` is stored at rule offset `+0x04` and is consumed as the secondary/background/outline/shadow color depending on draw mode.
- the byte-sized `m_effect` argument is stored at rule offset `+0x08` low byte; the high three bytes are padding/reserved and should not be widened into a 32-bit mode field.
- `m_alignment` is stored at rule offset `+0x0c`.
- when `m_rules._Last != m_rules._End`, the record is written inline and `m_rules._Last` advances by 16 bytes.
- when full, it calls the vector growth helper at `0x0049ac60` with the vector triplet, insertion pointer, and rule address.

The first-draft source uses `m_rules.push_back(rule)` for both the inline and slow-path append. Do not emit the vector growth helper as a source method, and do not initialize or name the three high bytes after `m_effect`. If a later deterministic-style pass zero-initializes the local rule, it must preserve the current caveat that the observed compiler shape only proves the low byte assignment.
