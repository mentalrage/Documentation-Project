# LodePNG Encode Front End `0x00443c80-0x00443e5d`

## Status

- Confidence: strong for behavior, library ownership, and upstream public symbol names.
- Proposed owner: [UID:0000KW][LodePNG](by-file/LodePNG.md)
- Disposition: bundled third-party LodePNG public encode APIs; exclude from NexusTK product source modules.
- Rebuild handling: vendor/rebuild from LodePNG source, not as NexusTK handwritten code.
- Autogen parent: intentionally unassigned because this page is excluded from project-code reconstruction.
- Evidence basis: read-only IDA MCP lookup, decompile, caller/callee, and string checks on 2026-05-24 and 2026-05-25 plus live IDA MCP lookup/caller/callee/decompile checks on 2026-06-05. The local comparison against the obtained LodePNG `20160501` source archive is previously recorded evidence; `wave3.py` was not executed for this pass.

## Exact Range Contents

| Range | Function | Role |
| --- | --- | --- |
| `0x00443c80-0x00443d61` | `lodepng_encode_memory` | Creates and initializes a stack `LodePNGState`, overrides both raw and PNG output color type/bit depth, calls the main encoder at `0x004466b0`, copies `state.error`, then frees state-owned memory. |
| `0x00443db0-0x00443e32` | `lodepng_encode_file` | Encodes PNG bytes, saves the encoded buffer through the stock disk helper behavior, frees the buffer, and returns LodePNG error `79` when file open fails. |
| `0x00443e40-0x00443e5d` | `lodepng_encode32_file` | Calls `lodepng_encode_file(fileName, pixels, width, height, LCT_RGBA, 8)`. |

## Behavior Notes

- Live IDA MCP decompile on 2026-06-05 reconfirmed the wrapper chain: `sub_443C80` constructs a stack `LodePNGState`, calls `sub_4460F0`, sets the caller-supplied color type and bit depth in both color-mode records, calls `sub_4466B0`, frees state-owned memory, and returns the captured LodePNG error value.
- Live decompile reconfirmed `sub_443DB0` calls `sub_443C80`, opens the output file with mode `wb`, writes the encoded buffer, closes the file, frees the buffer, and returns error `79` on file-open failure.
- Live decompile reconfirmed `sub_443E40` is a thin wrapper around `sub_443DB0(FileName, pixels, width, height, 6, 8)`.
- `0x00443c80` stores `LodePNGState::vftable`, calls `lodepng_state_init` at `0x004460f0`, writes caller-supplied color type and bit depth into both relevant color-mode records, and calls `lodepng_encode` at `0x004466b0`.
- The wrapper at `0x00443e40` fixes PNG color type `6` and bit depth `8`, which matches upstream `lodepng_encode32_file` and the screenshot RGBA8 output path.
- `0x00443db0` is not NexusTK-local file-output glue. It matches upstream `lodepng_encode_file`: encode to memory, save bytes to a file, free the encoded buffer, and return the encode/save error.

## Caller And Callee Evidence

- IDA lookup confirms function sizes: `0x00443c80` size `0xe1`, `0x00443db0` size `0x82`, and `0x00443e40` size `0x1d`.
- Live IDA callers on 2026-06-05 show `0x00443c80` is called by `lodepng_encode_file` at `0x00443db0` and by internal LodePNG helpers at `0x00444480` and `0x004445b0`.
- Live IDA callers show `0x00443db0` is called only by `lodepng_encode32_file` at `0x00443e40`.
- Live IDA callers show `0x00443e40` is called only by PNG screenshot capture at `0x00557e80`.
- Live IDA callees show `0x00443c80` calling `0x004460f0`, `0x004466b0`, `0x00444f50`, allocator cleanup, and security-check support; `0x00443db0` calling file I/O plus `0x00443c80`; and `0x00443e40` calling only `0x00443db0`.
- IDA callees show `0x004466b0` fans into many local `0x0044xxxx`/`0x0045xxxx` helpers, consistent with a bundled codec implementation rather than a tiny project-owned writer.
- A 2026-05-24 IDA callgraph rooted at `0x00443c80`, `0x00443db0`, `0x00443e40`, and `0x004466b0` reaches 73 modeled LodePNG helper functions through `0x00450b5e`. A 2026-05-25 follow-up keeps `0x00450b60-0x00450c9f` with LodePNG and excludes the old `0x00450ca0+` tail as MiniMap/shared support code.
- The obtained `lodepng-20160501` source archive contains the matching public functions `lodepng_encode_memory`, `lodepng_encode_file`, and `lodepng_encode32_file` in the same wrapper relationship observed here.

## Ownership Decision

The full range belongs to [UID:0000KW][LodePNG](by-file/LodePNG.md). Earlier docs treated `0x00443db0` and `0x00443e40` as project-facing wrappers, but source comparison shows they are stock LodePNG disk/public convenience APIs. [UID:0000K4][ImageWriters](by-file/ImageWriters.md) should document the screenshot dependency on these APIs, not own them as NexusTK source.

Do not treat `0x00443c80` as screenshot-specific even though the current project-facing path reaches it from screenshot PNG output.
