# 0x0049ba30-0x0049bad9 MSVC Aligned Array Allocation Helpers

## Status

- Disposition: ignored as standalone NexusTK source; rebuild through compiler/runtime support.
- Rebuild handling: third-party/runtime compiler allocation glue.
- Entity kind: compiler/runtime allocation helper.
- Confidence: strong for helper behavior, IDA function boundaries, caller refs, callees, cookie/alignment validation, padding, and ignored/not-reconstructable disposition.

## Covered Ranges

| Range | IDA Name | Role |
| --- | --- | --- |
| `0x0049ba30-0x0049ba92` | `sub_49BA30` | Allocate `count * 16` bytes, using ordinary `operator new` for small allocations and 32-byte aligned allocation with a back-pointer cookie for large allocations. |
| `0x0049ba92-0x0049baa0` | padding | `0xcc` alignment padding. |
| `0x0049baa0-0x0049bad9` | `sub_49BAA0` | Free a buffer allocated by the paired helper, validating the large-allocation back-pointer before calling the common free helper. |

## Rebuild Handling

Do not port these as handwritten project logic. Treat them as MSVC-generated allocation support emitted for code that needs 16-byte element arrays and 32-byte alignment on large allocations. The rebuilt project should rely on the compiler/runtime or a small local allocator only where source-level semantics require it.

## Raw Behavior Evidence

- `sub_49BA30` multiplies the requested element count by `16`.
- For sizes under `0x1000`, it calls `operator new(size)` directly.
- For large sizes, it allocates `size + 35`, aligns the returned pointer with `& 0xffffffe0`, and stores the original allocation at `aligned[-1]`.
- `sub_49BAA0` recomputes `count * 16`; for large allocations it checks that the stored original pointer is within the expected `0x1f` byte alignment window, then frees the original pointer.
- Both helpers call `_invalid_parameter_noinfo_noreturn` on impossible or corrupted allocation state.

## Evidence Notes

- IDA MCP reports `sub_49BA30` size `0x62` and `sub_49BAA0` size `0x39`.
- IDA callers for allocation are `sub_49AC60` and `sub_49ADA0`; callers for free are `sub_49ADA0` and `sub_4CE1B0`.
- The paired cookie/back-pointer pattern is runtime/compiler allocation glue, not a distinct NexusTK class method.

Live IDA MCP evidence from 2026-06-05:

- `lookup_funcs` reconfirms `sub_49BA30` at `0x0049ba30` size `0x62`, `sub_49BAA0` at `0x0049baa0` size `0x39`, no function at `0x0049ba92` or `0x0049bad9`, and the next project-owned `Crasher` constructor at `0x0049bae0`.
- `decompile 0x0049ba30` shows the `16 * count` byte-count calculation, overflow guard, direct `operator new` path for small nonzero sizes, large-allocation `size + 35` path, 32-byte alignment mask `0xffffffe0`, and stored original-pointer cookie at `aligned[-1]`.
- `decompile 0x0049baa0` shows the matching free helper: recomputes `16 * count`, validates the large-allocation cookie is within the `0x1f` alignment window, substitutes the stored original allocation pointer, and calls the common free helper.
- `callers`/`xrefs_to` report allocation helper calls at `0x0049acb4` and `0x0049ae63`, and free-helper calls at `0x0049ae37` and `0x004ce20e`.
- `callees` reports `operator new` and `__invalid_parameter_noinfo_noreturn` from the allocation helper, and `__invalid_parameter_noinfo_noreturn` plus `sub_5C7526` from the free helper.
- Raw bytes from `0x0049ba92-0x0049baa0` are fourteen `0xcc` alignment bytes; the following `0x0049bad9-0x0049bae0` padding is tracked separately in [UID:0000VN][-ignored](by-memory/-ignored.md).
- The helper is marked `RECONSTRUCTABLE:FALSE` because final source should express the allocating container/use site while compiler/runtime support regenerates this aligned allocation glue.
