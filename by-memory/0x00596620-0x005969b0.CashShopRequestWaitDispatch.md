struct ThreadMessage
{
    int messageId;       // +0x00
    int arg1;            // +0x04
    int arg2;            // +0x08

## Exact ThreadProc Child Correction

[UID:0004CL][0x00596810-0x00596915.ThreadProc](by-memory/0x00596810-0x00596915.ThreadProc.md) supersedes the older aggregate wording that said the worker drains the priority queue and then the default queue. The live body has one `RingBuffer::Dequeue` call. After a primary wake it calls `OnDispatchBegin`, queries `m_priorityQueue->IsEmpty()`, falls back to `m_messageQueue->IsEmpty()` only when needed, selects one nonempty queue, and dequeues exactly one 24-byte `ThreadMessage`. Producer helpers release the primary semaphore once for each queued record, so later records receive later wake iterations.

For an asynchronous record (`resultEvent == NULL`), the worker calls `OnMessage(messageId, arg1, arg2)`. For a synchronous record it calls `OnMessageEx(messageId, syncArg1, syncArg2, arg1, arg2)`, locks `m_resultMonitor`, reads the inline `m_resultList->GetCount()`, obtains entries through virtual `m_resultList->GetElementAt(index)`, and writes only the `result` member of the caller-created entry whose event matches. It does not allocate, append, or remove a `ThreadResultEntry`. It unlocks before `SetEvent(resultEvent)`, and signaling still occurs if the scan finds no matching entry.

The command-id-2 `WaitForQueueDrain` helper remains a real barrier: its caller creates and registers the result entry before enqueueing the synchronous no-op. That barrier property does not turn `ThreadProc` itself into a queue-draining loop. After any non-stopping wait iteration, including timeout/failure and secondary-handle routes, the worker calls `OnIdle`; the older `OnDispatchEnd` label was too narrow for the observed control flow.

## Command Id 2 Barrier Proof

`Thread::WaitForQueueDrain()` at `0x00596620` queues `{2,0,0,event,0,0}` and waits for the event. Socket's async command dispatcher at `0x00575e60` handles ids `3` through `14`, so id `2` falls through to base async handling. Socket's sync handler at `0x00576200` handles only id `0x0c` specially and otherwise tails to base `Thread::OnMessageEx`, which returns `0`. That makes id `2` a synchronous no-op work item used as a queue-drain barrier after earlier queued work, not a CashShop or Socket request operation.
