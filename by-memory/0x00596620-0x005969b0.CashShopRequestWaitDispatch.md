# 0x00596620-0x005969b0 Thread Message Dispatch Helpers

## Status

- Disposition: reconstructable NexusTK project code
- Entity kind: base-thread wait/result/message dispatch helper subrange
- Previous/stale generated owner: [UID:00001H][CashShopRequest](by-class/CashShopRequest.md) for `0x00596620` and `0x00596760`.
- Current source owner decision: [UID:0000OR][Thread](by-file/Thread.md). This is the generic queue, wait-handle, and virtual-dispatch portion of the base `Thread` island, not cash-shop-specific code.
- Rebuild handling: source-authored utility/threading code with internal compiler alignment padding between small helper bodies.
- Confidence: strong for IDA function boundaries, generic `Thread` ownership, queue/event behavior, and caller diversity; medium for final source-level helper names and the adjacent raw helpers.
- Reconstruction state: reconstructable and parent-attached, but no C++ is emitted because the final field names, helper names, and raw helper split are below the 95+ final-source gate.

## Covered Range

| Range | Current role | Notes |
| --- | --- | --- |
| `0x00596620-0x0059675e` | synchronous send-and-wait helper | Creates an event, registers it in the result list at `this+0x58` under the monitor/lock at `this+0x54`, enqueues request code `2` into queue `this+0x4c`, releases semaphore `this+0x0c`, waits, removes the result entry, closes the event, and unlocks. |
| `0x0059675e-0x00596760` | padding | Two `0xcc` alignment bytes before the explicit result-wait helper. |
| `0x00596760-0x005967c7` | wait-for-result helper | Waits on a caller-provided event, scans the result list for a matching event handle, returns the stored result payload if present, closes the event, removes the list entry, and unlocks. |
| `0x005967c7-0x005967d0` | padding | Nine `0xcc` alignment bytes before the socket-facing wait-handle registration helper. |
| `0x005967d0-0x005967e5` | add wait handle helper | Appends one handle at `this+0x0c + 4*waitCount` and increments the signed byte wait count at `this+0x08`; currently also documented in [UID:0001JZ][0x005967d0-0x005967e5.SocketThreadEvent](by-memory/0x005967d0-0x005967e5.SocketThreadEvent.md) because the observed direct caller is Socket setup. |
| `0x005967e5-0x005967f0` | padding | Eleven `0xcc` alignment bytes before an IDA-modeled raw helper alias. |
| `0x005967f0-0x00596805` | remove last wait handle helper | Decrements `this+0x08` and clears the last handle slot. IDA names it with a stale `sub_577A80` alias and reports no direct callers to this start. |
| `0x00596805-0x00596810` | padding | Eleven `0xcc` alignment bytes before `Thread::ThreadProc`. |
| `0x00596810-0x00596915` | `Thread::ThreadProc` | Sleeps briefly, waits on the base semaphore and registered handles, drains the async/sync queues, dispatches virtual message handlers, stores sync results in the result list, signals event-backed callers, and exits when the stop flag at `this+0x64` is set. |
| `0x00596915-0x00596920` | padding | Eleven `0xcc` alignment bytes. |
| `0x00596920-0x00596931` | base async message handler | Sets stop flag `this+0x64` when message id is `1`. |
| `0x00596931-0x00596940` | padding | Fifteen `0xcc` alignment bytes. |
| `0x00596940-0x0059695e` | base sync message handler | Sets stop flag `this+0x64` when message id is `1` and returns `0`. |
| `0x0059695e-0x00596960` | padding | Two `0xcc` alignment bytes. |
| `0x00596960-0x005969b0` | async queue-post helper | Packs a six-dword request record into queue `this+0x4c` and releases semaphore `this+0x0c`. |

The next raw helper at `0x005969b0-0x00596a00` is a sibling queue-post helper that writes to queue `this+0x50`; it is outside this page's end-exclusive range and should be split or documented with the `0x00596a00` sync-post family, not folded into this item.

## Evidence

- 2026-06-02 IDA MCP `lookup_funcs` confirms modeled starts and sizes: `0x00596620` size `0x13e`, `0x00596760` size `0x67`, `0x005967d0` size `0x15`, `0x005967f0` size `0x76` under a stale name alias, `0x00596810` size `0x105`, `0x00596920` size `0x11`, `0x00596940` size `0x1e`, and `0x00596960` size `0x50`. `0x005969b0` is not an IDA function start even though disassembly shows raw helper bytes there.
- IDA MCP decompilation of `0x00596620` shows event creation through `dword_69BE3C`, insertion into the result-list object at `this+0x58`, queue record `{2,0,0,event,0,0}` enqueued through queue `this+0x4c`, `ReleaseSemaphore(this+0x0c)`, `WaitForSingleObject`, list scan/removal, `CloseHandle`, and monitor unlock.
- IDA MCP decompilation of `0x00596760` shows wait/result retrieval over the same result-list and lock fields: `WaitForSingleObject(event)`, lock `this+0x54`, scan `this+0x58`, return entry payload at offset `+4`, close the event, remove the entry, and unlock.
- IDA MCP disassembly of `0x005967d0` shows a compact append helper: use signed wait-count byte at `this+0x08`, store a handle into the wait-handle array at `this+0x0c`, increment the count, and return.
- IDA MCP disassembly of `0x005967f0` shows a compact remove helper: decrement `this+0x08`, sign-extend the previous count, and zero the corresponding wait-handle slot. The decompiler displays a misleading mixed decompile with addresses from `0x00577a80`, so use the disassembly bytes for this helper.
- IDA MCP decompilation/disassembly of `0x00596810` shows the base worker loop waiting on registered handles via `WaitForMultipleObjects`, draining queues at `this+0x50` and `this+0x4c`, invoking virtual slots at vtable offsets `0x24`, `0x2c`, `0x30`, `0x34`, storing sync results, and signaling events with `SetEvent`.
- IDA MCP decompilation of `0x00596920` and `0x00596940` shows the base stop-message behavior: message id `1` sets byte `this+0x64`; the sync handler returns `0`.
- IDA MCP decompilation of `0x00596960` shows a six-dword record `{msg,param1,param2,0,0,0}` enqueued through `this+0x4c`, followed by `ReleaseSemaphore(this+0x0c)`.
- 2026-06-02 IDA MCP caller evidence is broad and not cash-shop-specific: `0x00596620` has callers from main-menu/terminal/help-style UI ranges, `0x00596760` has callers from main-menu, pane/list handling, and terminal, `0x005967d0` has one Socket setup caller at `0x005764cc`, `0x00596920` has MiscWorkThread and Socket-derived callers, and `0x00596960` is reached by downloader, MiscWorkThread, and packet-send helper families.
- Existing [UID:0000OR][Thread](by-file/Thread.md) and [UID:0001JX][0x00596250-0x0059756e.ThreadAndThreadMan](by-memory/0x00596250-0x0059756e.ThreadAndThreadMan.md) already identify `0x00596620`, `0x00596760`, `0x00596810`, `0x00596920`, `0x00596940`, and `0x00596960` as base `Thread` helpers with stale CashShop ownership in generated output.

## Ownership Decision

Treat this range as generic [UID:0000OR][Thread](by-file/Thread.md) infrastructure. The old `CashShopRequestWaitDispatch` name is retained in the filename for now only as a stable path and historical generated-owner clue; the documented behavior is base thread queueing, waiting, result handoff, and virtual message dispatch.

Do not use this page as proof that [UID:0000I0][CashShopRequest](by-file/CashShopRequest.md), [UID:0000Q5][g_packetSender](by-global/g_packetSender.md), or [UID:0000QH][g_pCashShopRequest](by-global/g_pCashShopRequest.md) own the base queue primitives. CashShop/FileDownloader/Socket-derived code calls into this thread abstraction.
