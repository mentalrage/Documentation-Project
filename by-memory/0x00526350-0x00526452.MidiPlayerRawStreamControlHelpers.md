## Source Placement, Naming, And Split Rationale

The owner/emitter remains [UID:0000LD][MidiPlayer](by-file/MidiPlayer.md). These are private `MidiPlayer.cpp`/WinMM stream-control helpers, not `MidiPlayer` class methods: the raw bodies do not use `this`, `ecx` object state, or class field offsets. They operate on file-static WinMM/MIDI state and imported WinMM APIs.

`OpenSelectedMidiFileNoRestart` is intentionally distinct from [UID:0001CH][0x00526100-0x00526332.MidiPlayerTrackSelectionHelpers](by-memory/0x00526100-0x00526332.MidiPlayerTrackSelectionHelpers.md) `StartSelectedMidiFile`. The [UID:0001CH][0x00526100-0x00526332.MidiPlayerTrackSelectionHelpers](by-memory/0x00526100-0x00526332.MidiPlayerTrackSelectionHelpers.md) helper copies/selects a path and performs reset/open/restart/volume behavior; this helper copies the path and opens/primes without restart or volume application. `RestartSelectedMidiStream` also does not call `ApplyMidiVolume`, which is another reason not to merge it with the track-selection/start helper.

No further split is recommended. The three raw helpers are tiny, contiguous, source-adjacent bodies separated only by compiler alignment, all share the same file owner, the same raw/no-route caveat, the same WinMM state globals, and the same reset/open helper dependencies. Splitting them into three pages would duplicate the same evidence and create UID/registry churn without improving source placement. The current page should remain the durable home for the cluster while documenting each subrange separately.

The source-facing names in the formal C++ and this page are reconstructed/source-shaped names, not original-symbol claims. They are retained because they describe the exact byte behavior better than raw address labels and are consistent with the surrounding MidiPlayer source family.
