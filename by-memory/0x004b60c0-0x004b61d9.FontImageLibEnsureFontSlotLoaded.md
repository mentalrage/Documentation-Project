## Behavior

This method lazily opens one of the two bitmap-font archives and builds the in-memory glyph pointer table for that slot.

Observed flow from live IDA:

- clamps negative font ids and ids greater than or equal to `2` back to slot `0`;
- computes a slot window at `this + 0x40008 * slotIndex`, with the actual [UID:0001UM][FontSlotStorage](by-type/by-struct/FontSlotStorage.md) object beginning at `slotWindow + 0x04`;
- if the archive pointer at `slotWindow + 0x04` is already non-null, returns `slotWindow + 0x04`;
- formats a UTF-16 archive/resource name with `BARAM%02d.EFT`;
- allocates and constructs a `DATFile` object;
- opens `BARAM00.EFT` or `BARAM01.EFT` through the `DATFile` virtual `Open` slot;
- obtains the current entry payload base through [UID:0000IN][DATFile](by-file/DATFile.md) method `DATFile::GetDataPointer` at `0x0049c550`;
- reads two 16-bit slot metrics through the `DATFile::Read` virtual slot into `slotWindow + 0x08` and `slotWindow + 0x0a`;
- subtracts `4` from the second metric at `slotWindow + 0x0a`;
- reads `0x10000` 32-bit glyph offsets;
- for each nonzero offset, stores `payloadBase + offset` into the glyph pointer table at `slotWindow + 0x0c + 4 * glyphId`;
- stores `0` for zero offsets;
- returns the [UID:0001UM][FontSlotStorage](by-type/by-struct/FontSlotStorage.md) base at `slotWindow + 0x04`.

The IDA decompiler currently uses an unsigned argument type, but the assembly tests the sign bit before the `>= 2` comparison:

```text

4b60ee  test    edx, edx

4b60f2  cmp     edx, 2
4b60f5  jl      short loc_4B60F9
4b60f7  xor     edx, edx
```

So the source-level slot index should be treated as a signed or range-checked font id, not as a pure unsigned modulo-style value.
