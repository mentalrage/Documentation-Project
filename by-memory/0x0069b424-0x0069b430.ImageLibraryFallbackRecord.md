# 0x0069b424-0x0069b430 ImageLibraryFallbackRecord

## Summary

- Address range: `0x0069b424-0x0069b430`
- Entity kind: 12-byte monster-image table fallback/default object
- Static image value pattern: three initialized dwords, all `0xffffffff`
- Disposition: reconstructable NexusTK global data
- Rebuild handling: `source-declared/generated-binary`
- Confidence: strong for layout, lifetime, fallback use, and loader writes; medium for final source-facing name and owner module
- Parent status: intentionally unparented because the final owner could be concrete `MonsterImageLib.cpp` storage or shared monster/riding table-helper module storage.
- Reconstruction note: C++ intentionally left blank because final source name and owner placement are not final-source quality.

This range is a static 12-byte outer table object used by the monster image table code. Live IDA shows it is constructed during static initialization, destroyed during static shutdown, allocated with `0x15` nested group slots by the monster table loader, seeded with default one-entry group records, and returned by the monster table lookup helper when a requested table index is out of range.

The existing filename says "fallback record"; the stronger current interpretation is "fallback/default table object." It is not the separate 10-byte inner frame fallback at `0x0066deb0`, which is returned by the shared frame-entry lookup helpers.

## Lifetime And Behavior

The static initialization wrapper at `0x00419fb0-0x00419fc6` calls the table-object initializer on this range and registers `0x0060c280` for shutdown cleanup. The initializer at `0x00528930-0x00528947` zeroes all three dwords in the object.

The static cleanup wrapper at `0x0060c280-0x0060c28a` calls the cleanup helper at `0x00528950-0x005289c6`. That helper reads the entry pointer from the third dword, destroys each 8-byte group record when the pointer is non-null, frees the backing allocation, clears the count byte inside the middle field, and clears the entry pointer.

The monster table loader at `0x004dac40-0x004daebd` uses this object as a default/fallback outer table:

1. It reads the monster table count from the resource stream and allocates the owning instance table for loaded monster rows.
2. It calls the shared outer-table allocation helper on this static object with count `0x15`.
3. It walks `0xa8` bytes as `0x15` eight-byte child groups through the entry pointer at `0x0069b42c`.
4. For each group, it allocates one 10-byte frame entry and seeds that entry with start `0`, end `30000`, and flag byte `0`.
5. It then parses the resource-backed monster table rows into the owning instance table.

The small monster table lookup at `0x004db330-0x004db353` returns `loadedTableBase + 12 * index` when the index is in range; otherwise it returns the address `0x0069b424`. This proves the static object is the out-of-range outer-table fallback for monster image table lookups.
