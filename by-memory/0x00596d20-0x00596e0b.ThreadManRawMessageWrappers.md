## Boundary Notes

These raw starts sit between modeled `ThreadMan::ThreadMan` at `0x00596bf0-0x00596d13` and the modeled worker loop at `0x00596e10-0x005970df`. IDA currently does not model any start in this page as a function, but the disassembly has aligned method-shaped entries and concrete `PostThreadMessageW` calls.

The non-deleting destructor here shares core cleanup behavior with the scalar deleting destructor at `0x005974f0`. The scalar deleting wrapper is the vtable slot; this raw destructor is still project code and should be kept in the `ThreadMan` source family.

B008 2026-06-19 local PE/Capstone recheck reconfirmed the raw destructor body at `0x00596d20-0x00596d6a`: it restores the `ThreadMan` vtable, terminates/closes/clears `m_workerThreadHandle`, deletes/nulls `m_watchList`, clears [UID:0000SH][g_pThreadMan](by-global/g_pThreadMan.md), and tail-jumps to `LObject` cleanup at `0x004f4a90`. This raw body is the best current evidence for ordinary source-level `ThreadMan::~ThreadMan()`; [UID:0001K5][0x005974f0-0x0059756e.ThreadManScalarDeletingDestructor](by-memory/0x005974f0-0x0059756e.ThreadManScalarDeletingDestructor.md) duplicates that cleanup and then applies generated deleting flags.

B009's older Rule 26 report correctly identified `[0x00596d20,0x00596d6f)` as the ordinary destructor and excluded scalar flags, `OperatorDeleteWrapper`, guard-helper logic, vtable stores, and an explicit `LObject::~LObject()` call from handwritten source. Its recommendation to write `g_pThreadMan = NULL;` directly in the derived body is retained as a historical pre-PMD assumption; current direct-base evidence moves that statement into `Singleton<ThreadMan>::~Singleton()`.

B012 independently rechecked the raw ordinary destructor against [UID:0001K5][0x005974f0-0x0059756e.ThreadManScalarDeletingDestructor](by-memory/0x005974f0-0x0059756e.ThreadManScalarDeletingDestructor.md). The `0x00596d20-0x00596d6f` body restores the `ThreadMan` vtable, terminates/closes/nulls `m_workerThreadHandle`, virtual-deletes/nulls `m_watchList`, clears `g_pThreadMan`, and tail-jumps to `LObject` cleanup without deleting flags or storage release. This is the best source-shape evidence for `ThreadMan::~ThreadMan()`. B012 also found zero VA pointer hits and zero rel32 hits for this raw destructor and the message-wrapper starts, so direct reachability remains open without changing the source-shape conclusion.

Current correction: ThreadMan RTTI has direct empty `Singleton<ThreadMan>` at PMD `{4,-1,0}`. Reverse destruction order is derived cleanup, Singleton-base destructor/clear, then `LObject` base destruction. Therefore the observed clear remains exact binary behavior, but the formal handwritten `ThreadMan::~ThreadMan()` removes only the explicit assignment and relies on the accepted Singleton destructor specialization. The five wrapper bodies remain unchanged.
