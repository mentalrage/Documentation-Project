## Behavior Details

Disassembly and decompile agree on the concrete constructor behavior:

- `ECX` is the destination vector header (`begin`, `end`, `capacityEnd`).
- The header words at `this[0]`, `this[1]`, and `this[2]` are zeroed before allocation.
- `count == 0` returns the zeroed header.
- `count > 0x3fffffff` calls [UID:0002E1][0x00421500-0x0042151a.MsvcVectorThrowHelpers](by-memory/0x00421500-0x0042151a.MsvcVectorThrowHelpers.md). `0x3fffffff` is 1073741823 (Verified with `tools/int_convert.py`).
- `byteCount = count * 4`.
- Requests below `0x1000` bytes use direct `operator new(byteCount)`. `0x1000` is 4096 (Verified with `tools/int_convert.py`).
- Large requests allocate `byteCount + 0x23`, align `(raw + 0x23) & ~0x1f`, and store the raw allocation pointer at `aligned[-1]`. `0x23` is 35 and `0x1f` is 31 (Verified with `tools/int_convert.py`).
- The fill loop loads `*fillValue`, writes one dword, advances by four bytes, and repeats until the requested count is filled.
- Final pointer updates set `begin`, `end`, and `capacityEnd` to the allocated span and return `this`.
- The function returns with `retn 0Ch`, proving three stack arguments after `this`: count, fill-value reference/pointer, and an unused allocator-like argument.

That `retn 0Ch` ABI is important source-quality evidence. A final two-argument `UInt32Vector::UInt32Vector(uint32_t count, const uint32_t* fillValue)` body would be decompiler-shaped and would hide the allocator-like third argument expected from a lowered `std::vector<unsigned int>` fill constructor.
