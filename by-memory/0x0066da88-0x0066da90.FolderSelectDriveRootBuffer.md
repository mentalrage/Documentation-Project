# 0x0066da88-0x0066da90 FolderSelect Drive Root Buffer

## Summary

- Address range: `0x0066da88-0x0066da90`
- Entity kind: initialized mutable wide-character buffer
- Disposition: reconstructable project data
- Rebuild handling: `source-declared/generated-binary`
- Confidence: strong for `FolderSelectDialog` use
- Parent status: assigned to direct file parent [UID:0000JF][FolderSelectDialog](by-file/FolderSelectDialog.md), now implemented at `95/96`.
- Direct source owner: [UID:0000JF][FolderSelectDialog](by-file/FolderSelectDialog.md). The accepted source-facing name is `s_driveRootBuffer` because both the constructor and retained drive helper mutate the first WCHAR. The weaker `s_driveRootName` spelling remains historical naming uncertainty, not the emitted declaration.
- Source declaration: file-static mutable `wchar_t[]`, emitted at source position `5` before FolderSelectDialog method bodies. This is shared initialized storage rather than a class-relative field, stack temporary, or read-only literal.

This `0x8`-byte buffer, 8 decimal bytes (Verified with `int_convert.py`), stores a mutable wide drive-root string for folder selection. The initial bytes decode as `X:\\` plus terminator, and [UID:000457][0x004b1590-0x004b18d6.FolderSelectDialogConstructor](by-memory/0x004b1590-0x004b18d6.FolderSelectDialogConstructor.md) plus [UID:00045A][0x004b1a00-0x004b1b05.FolderSelectDialogPopulateDriveList](by-memory/0x004b1a00-0x004b1b05.FolderSelectDialogPopulateDriveList.md) rewrite the drive letter before creating drive-list entries. It is file/static dialog state, not FolderTreePane state and not MusicControlDialog state.

The four checked references close the known user set: constructor write/use at `0x004b183f` / `0x004b185b` and retained-helper write/use at `0x004b1a8b` / `0x004b1aaa`. Each user changes only code unit zero and synchronously passes the resulting root to `StringMenuItem(const wchar_t *)`, which copies it into owned inline `m_text[0x80]`. No item retains this mutable pointer. The shared file-static object is consequently non-reentrant and not thread-safe, but no asynchronous or overlapping user is evidenced.
