## IDA MCP Boundary Notes

- `0x0049bd20-0x0049bd2c` is a 12-byte non-modeled forwarder body; `0x0049bd2c-0x0049bd30` is four bytes of `0xcc` padding before this aggregate's first modeled constructor.
- `0x0049bd30-0x0049be41` is the modeled public constructor body. The raw byte sweep contains one literal `0xcc` byte inside instruction/immediate data, so padding decisions must use disassembly boundaries rather than byte-count alone for this constructor.
- `0x0049be41-0x0049be70` contains constructor tail cleanup/destructor helper code plus alignment before the public load/index forwarder at `0x0049be70`.
- `0x0049be70-0x0049be7c` is the public load/index forwarder and `0x0049be7c-0x0049be80` is four bytes of `0xcc` padding before `DATFileContainer::DATFileContainer`.
- `0x0049d6ed-0x0049d6f0` is three bytes of `0xcc` padding after `_DATFileMgr::FindNodeByKey` and before the following `DescPane` range.

## Ownership Decision

These ranges belong together in `archive/DATFileMgr.cpp`. The current Wave3 split into separate one-class files is a staging artifact, not strong evidence of original source layout. The per-entry reader belongs in the companion [UID:0000IN][DATFile](by-file/DATFile.md) module.

The small [UID:000227][0x0049bd20-0x0049bd2c.DATFileMgrFindEntryForwarder](by-memory/0x0049bd20-0x0049bd2c.DATFileMgrFindEntryForwarder.md) and `0x0049be70` wrappers should be kept as `DATFileMgr` methods. Live IDA/raw disassembly shows method-style `this` access and direct forwarding into the internal manager.

`DATIndexVector` should stay in a standalone [UID:0000IP][DATIndexVector](by-file/DATIndexVector.md) helper file unless later source-layout evidence proves a different common folder.
