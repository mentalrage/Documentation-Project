## Behavior

This method finalizes a decoded 16-bit pixel buffer after image-loader code has filled the `EPFTileContext` primary pixel data. If `g_surfaceUsesRgb565Pixels` / raw `byte_69B3D5` is clear, it calls the compatibility pixel transform [UID:0003ZP][0x004bb0e0-0x004bb111.ConvertRgb565ToRgb555Pixels](by-memory/0x004bb0e0-0x004bb111.ConvertRgb565ToRgb555Pixels.md) over the decoded pixel buffer.

The pixel count is computed from the context bounds:

```text
(0x04) pixelData
(0x10) left
(0x14) top
(0x18) right
(0x1c) bottom
count = (right - left) * (bottom - top)
```

Raw decompilation shape:

```c
void __thiscall sub_458560(int this)
{
    if (!byte_69B3D5)
        sub_4BB0E0(*(unsigned __int16 **)(this + 4),
                   (*(int *)(this + 24) - *(int *)(this + 16)) *
                   (*(int *)(this + 28) - *(int *)(this + 20)));
}
```

`sub_4BB0E0` iterates `count` 16-bit pixels and rewrites each value as `(pixel & 0x001f) | ((pixel >> 1) & 0x7ff0)`. The expression is intentionally preserved as observed rather than normalized to canonical `0x7fe0`: source green bit 5 and source blue bit 4 both feed destination bit 4 through OR. The source-facing count remains signed `int`; valid decoder geometry supplies a nonnegative product. Zero returns in the callee before pointer use, while a malformed negative product would follow the callee's nonzero countdown through its 32-bit residue and is not hardened to a `> 0` loop.

The D5 flag is source-facing `g_surfaceUsesRgb565Pixels`. Surface initialization sets it for 32-bit output and for 16-bit surfaces whose green mask is `0x07e0`; 24-bit and RGB555-compatible paths clear it. Therefore the zero branch here means that decoded RGB565 words require the compatibility transform before use by the active Surface path.

The helper has no alternate branch, no allocation, and no buffer lifetime side effects. If the render-mode byte is already set, it returns without mutating the context.

The accepted source-facing form remains exactly in the managed formal C++ header above; no second prose-only draft is maintained.

## Heuristic Naming And Type Resolution

`byte_69B3D5` should be documented as `g_surfaceUsesRgb565Pixels` in this context. The name is descriptive rather than proven-original, but it is stronger than a raw byte label: Surface initialization sets the byte for 32-bit output and 16-bit surfaces with green mask `0x07e0`, the callback table selects the RGB565-capable callback family when it is true, screenshot output expands RGB565 on the nonzero path, and alpha/palette consumers use the same polarity for 6-bit green versus compatibility handling. Rejected names include `g_newRenderingMode` because it is too broad, `g_highColorMode` because both RGB555 and RGB565 are high-color formats, and `g_is32BitMode` because a 16-bit RGB565 surface also sets the flag.

`0x004bb0e0` should be documented as `ConvertRgb565ToRgb555Pixels(unsigned short* pixels, int pixelCount)`. It preserves the low five bits, shifts the upper field, and keeps the exact noncanonical `0x7ff0` mask whose green-LSB/blue-MSB collision distinguishes it from a clean RGB565-to-RGB555 repack. It has one known caller, this method, no callees, no data refs, and no EPFTileContext receiver, so the helper is modeled as an externally linked stateless [UID:0000NT][SoftwareBlend16](by-file/SoftwareBlend16.md) primitive rather than as an EPFTileContext private method or a callback-table slot.

The field names used by the draft are source-facing working names already supported by EPFTileContext docs: `pixelData` at `+0x04`, and `bounds.left/top/right/bottom` at `+0x10/+0x14/+0x18/+0x1c`. B004's class-level pass later closed the broader EPFTileContext field questions to descriptive names (`pixelFormat`, `alphaData`, `encodedMaskByteCount`, and `encodedMaskBytes`), but this method remains independent of those fields because the body only reads the primary pixel pointer and rectangle bounds.
