## Behavior

This primary virtual paints the ranking-event scrollbar. It renders the track before and after the thumb with `SLIDEBG.EPF` / `SLIDEBG.PAL`, then renders the thumb/button with `SCRBUTT.EPF` / `BUTTON.PAL`.

The method:

- initializes a local EPF/tile context;
- obtains the pane clipping rectangle;
- exits or clears the whole clip when the scrollbar is not enabled or has no scrollable range, but only when `m_scrollStyle` is zero;
- computes the track segment rectangles inline from bounds `+0x44`, orientation `+0xfc`, current position `+0xfe`, max range `+0x100`, drag flag `+0xfb`, and drag anchor `+0x108`;
- intersects each segment with the clip rectangle before invalidation/drawing;
- clears inherited `m_drawMode`, selects draw colors `0` then `0x80`, and prepares each clipped pane region before drawing;
- draws vertical track fill/cap frames `1/0/2` and horizontal fill/cap frames `4/3/5`;
- computes the thumb rectangle through [UID:0001ZB][0x0045a710-0x0045a98a.RankingEventScrollPaneGetScrollRegionRect](by-memory/0x0045a710-0x0045a98a.RankingEventScrollPaneGetScrollRegionRect.md) with part `2`, then draws `SCRBUTT.EPF` frame `0` or `1` depending on whether hover part `+0x103` is `2`.

This is source-authored UI rendering, not compiler glue. It should move with the private ranking dialog controls.

For source reconstruction, the two track rectangles use `GetPartRect(kRankingScrollPartPageBeforeThumb/AfterThumb)` even though the optimized binary inlines those constant-part geometry paths and calls `0x0045a710` directly only for the thumb. This matches accepted sibling scrollbar source shape without losing the exact inline-geometry evidence below.
