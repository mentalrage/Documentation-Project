## Behavior

The helper opens `https://secure.kru.com/itemshop/data/itemshop.ver` with WinINet and sets the five `3000ms` timeout options in the observed order: connect, receive, send, data-send, and data-receive. Live MCP session `80de0a67` shows the status query uses `statusLength = 256` with `wchar_t statusText[128]`; the `HttpQueryInfoW(..., HTTP_QUERY_STATUS_CODE, ...)` return value is ignored and `_wtoi(statusText)` is evaluated unconditionally. A local `std::string responseText` is constructed before the status comparison.

On HTTP `200`, the worker queries numeric content length into a local dword, writes it to `CashShopVersionRequest::contentLength` at `+0x08`, then streams with a `char chunkBuffer[100000]` and no source-level cap on `available`. Each successful read null-terminates at `chunkBuffer[bytesRead]`, appends with `strlen(chunkBuffer)` rather than binary `bytesRead`, adds `bytesRead` into a local running count, writes `CashShopVersionRequest::bytesDownloaded` at `+0x0c`, and logs `Downloading : %d / %d\n` through a `wchar_t progress[256]`/`swprintf_s`-style formatter. The loop is `do/while (bytesRead != 0)`, so the terminal zero-byte read still passes through the append/progress block once. The compiler/decompiler path also shows a range-check edge before the null write when `bytesRead >= 100000`.

After download, the worker constructs `Json::Value root` then `Json::Reader reader`, calls `reader.parse(responseText, root, true)`, and retrieves `root.get("version", Json::Value())`. When the value is non-null, it converts to string and, if [UID:00028I][0x0067a73c-0x0067a740.g_pFittingRoomDialog](by-memory/0x0067a73c-0x0067a740.g_pFittingRoomDialog.md) is present, copies the version string to `g_pFittingRoomDialog->m_itemShopVersion` at `dword_67A73C + 0x790`. The target-specific cleanup path closes `remoteFile` and `internet` only after the parsed `version` value is non-null; early `remoteFile == NULL` closes only `internet`, while status-not-200, parse-failure, and null-version paths do not reach the final handle closes in the observed body.

`CashShopVersionRequest` is a `0x10` vtable payload with `state` at `+0x04`, `contentLength` at `+0x08`, and `bytesDownloaded` at `+0x0c`. The dispatcher, not this worker, destroys the version request after this helper returns. The fitting-room state write target is `g_pFittingRoomDialog->m_itemShopVersion` at `dword_67A73C + 0x790`; `+0x7a8` belongs to the catalog active-request slot, not this version string.
