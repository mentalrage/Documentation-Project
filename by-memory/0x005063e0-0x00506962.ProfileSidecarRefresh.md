# 0x005063e0-0x00506962 - Profile Sidecar Refresh

## Status

- Disposition: reconstructable NexusTK project code.
- Entity kind: selected-profile sidecar refresh and outbound profile packet helper.
- IDA function: `sub_5063E0`, size `0x582`.
- Confirmed source owner: [UID:0000MS][ProfileStorage](by-file/ProfileStorage.md).
- Rebuild handling: source-authored profile-storage/profile-image support.
- Confidence: strong for boundary, behavior, sidecar table, caller map, and ProfileStorage ownership; medium for final source-facing helper and field names.

## Address Range

| Range | Entity | Role |
| --- | --- | --- |
| `0x005063e0-0x00506962` | `RefreshSelectedProfileData` | Probes selected-profile image sidecars, optionally runs `FaceRipper.exe`, reads a `.jpf` profile blob, validates parsed dimensions, and queues request packet `79`. |

The preceding `0x005063db-0x005063e0` and following `0x00506962-0x00506970` spans are confirmed `0xcc` padding in [UID:0000VN][-ignored](by-memory/-ignored.md).

## Behavior

This function is shared by profile UI and a packet-driven `MapPane` path. IDA confirms callers at `0x00507c90`, `0x0053fdc0`, and `0x0053fe90`. The `0x0053fe90` caller is a tiny ProfileDialog-neighborhood wrapper with no direct xrefs, now documented at [UID:0001DU][0x0053fe90-0x0053fe9b.ProfileDialogRefreshHelper](by-memory/0x0053fe90-0x0053fe9b.ProfileDialogRefreshHelper.md). The file-path and selected-profile behavior make `0x005063e0` a good `profile/ProfileStorage.cpp` candidate, but packet ownership should be revisited when profile UI/network helpers are split.

`RefreshSelectedProfileData` uses the selected profile/name field at `g_pConfig + 0x2912b8`, checks image sidecars with extensions `bmp`, `pcx`, `jpg`, `jpeg`, and `pnm`, optionally launches `FaceRipper.exe`, and only sends a `.jpf` payload when the decoded portrait span is `48 x 56`. See [UID:0001QL][client_profile_storage](by-meta/client_profile_storage.md) for the sidecar protocol notes.

## Reconstruction Decision

Attach this helper to [UID:0000MS][ProfileStorage](by-file/ProfileStorage.md). The two external triggers are MapPane packet handling and ProfileDialog apply flow, but the body is selected-profile file/path/sidecar logic and the existing profile-storage docs already group the `.usr`, `.cfg`, and selected-profile sidecar helpers under `profile/ProfileStorage.cpp`.

Do not emit C++ yet. The helper is well understood, but the string/path helper names, packet writer names, and final `RegistryConfig` field names are still synthetic or only partially recovered.
