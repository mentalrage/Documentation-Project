## Behavior

This method expands one encoded glyph record into the shared `FontImageLib` scratch bitmap/tile buffer.

Observed flow:

- builds a destination rectangle from the glyph record:
  - left: `record + 0x04`;
  - top: `record + 0x02`;
  - right: `record + 0x08`;
  - bottom: `record + 0x06`;
- computes row width as `right - left`;
- ensures the shared scratch buffer at `this + 0x80014` is large enough for the decoded glyph;
- updates the scratch buffer capacity/size at `this + 0x80018`;
- optionally clears the scratch buffer before decoding;
- stores the scratch buffer pointer into the destination/tile context;
- starts encoded row decoding at `record + 0x0e`;
- processes one zero-terminated token stream per row;
- for each nonzero token:
  - low five bits are run length;
  - high three bits are palette index;
  - the palette index selects a byte from the caller-provided palette/remap table;
  - skip/transparent behavior changes depending on whether the destination was pre-cleared;
- advances to the next encoded row after each `0` terminator.

## FontGlyphRecord Evidence

The `lea edi, [record + 0x0e]` instruction proves that the encoded byte stream starts fourteen bytes after the record base. This confirms two 16-bit fields exist between `right` at `+0x08` and the encoded rows at `+0x0e`, even though their semantics remain unresolved.
