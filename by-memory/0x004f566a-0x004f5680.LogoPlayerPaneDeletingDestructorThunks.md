# 0x004f566a-0x004f5680 LogoPlayerPane Deleting Destructor Thunks

## Status

- Disposition: non-reconstructable compiler/linker-generated thunks from source class layout.
- Entity kind: secondary-base deleting destructor adjustor thunks.
- Rebuild handling: source-declared/generated-binary; the final class declarations should cause the compiler to emit these thunks, but this exact range must not be a standalone emitter.
- Owner class: [UID:00007H][LogoPlayerPane](by-class/LogoPlayerPane.md).
- Parent aggregate: [UID:00019D][0x004f53b0-0x004f570c.LogoPlayerPane](by-memory/0x004f53b0-0x004f570c.LogoPlayerPane.md).

## Behavior

The first thunk adjusts `this` by `-0xa0` and forwards to `0x004f5680`; the second adjusts `this` by `-0xa4` and forwards to `0x004f5680`. They are generated by the multiple-base/interface layout of `LogoPlayerPane` and should be reproduced by source declarations, not handwritten as source functions.

The decompiler prints these as `this - 40` and `this - 41` because it typed `this` as `_DWORD *`; the instruction bytes and disassembly show byte adjustments of `0xa0` and `0xa4`.

## Source Policy

No standalone C++ should be emitted for this range. The two bodies are exact MSVC deleting-destructor adjustor thunks: they adjust an incoming secondary or tertiary base pointer back to the complete `LogoPlayerPane` object and tail-jump to [UID:0002PY][0x004f5680-0x004f570c.LogoPlayerPaneScalarDeletingDestructor](by-memory/0x004f5680-0x004f570c.LogoPlayerPaneScalarDeletingDestructor.md). The source-side requirement is an ordinary `LogoPlayerPane` declaration and virtual destructor in [UID:0000O4][StartupLogoPanes](by-file/StartupLogoPanes.md), with the inherited Pane/EventHandler layout preserved so the compiler regenerates the vtable slots and adjusted-this thunks.

Keep [UID:00007H][LogoPlayerPane](by-class/LogoPlayerPane.md) as the semantic/class-layout owner, but leave `EMITTER_UIDS` blank. The direct policy precedent is [UID:0002PQ][0x004f52de-0x004f52f4.LogoPaneDeletingDestructorThunks](by-memory/0x004f52de-0x004f52f4.LogoPaneDeletingDestructorThunks.md): same two 11-byte `-0xa0`/`-0xa4` thunk pattern, same vtable-only reachability, same scalar deleting destructor target shape, and same no-handwritten-C++ treatment.

## Layout Meaning

The primary destructor table slot at `0x0061d018` points directly to `0x004f5680`. The secondary slot at `0x0061d070` is the deleting-destructor entry used when the object is viewed through the Pane/EventHandler subobject at object offset `+0xa0`; thunk `0x004f566a` subtracts `0xa0` to recover the complete object pointer. The tertiary slot at `0x0061d0a0` is the deleting-destructor entry for the timer/event view at object offset `+0xa4`; thunk `0x004f5675` subtracts `0xa4` before entering the same scalar deleting destructor.

These offsets are not arbitrary decompiler artifacts. They match the `LogoPlayerPane` constructor/destructor vtable stores at `+0`, `+0xa0`, and `+0xa4`, the [UID:0001VH][PaneLayout](by-type/by-struct/PaneLayout.md) base-object model, the derived event-handler route documented in [UID:0002PV][0x004f55d0-0x004f561d.LogoPlayerPaneInputSkipHandlers](by-memory/0x004f55d0-0x004f561d.LogoPlayerPaneInputSkipHandlers.md), and the parallel `LogoPane`/`VideoPlayerPane` destructor thunk families.
