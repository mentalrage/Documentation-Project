# LodePNGState Destructors `0x00448520-0x00448557`

## Status

- Confidence: strong for function boundaries and ownership.
- Proposed owner: [UID:00007E][LodePNGState](by-class/LodePNGState.md) inside [UID:0000KW][LodePNG](by-file/LodePNG.md)
- Evidence basis: `simroot_v2` active/disabled files, read-only IDA MCP lookup/decompile checks on 2026-05-24 and 2026-05-25, plus local comparison against the obtained LodePNG `20160501` header. `wave3.py` was not executed for this pass.

## Exact Range Contents

| Range | Function | Role |
| --- | --- | --- |
| `0x00448520-0x00448527` | `LodePNGState::~LodePNGState` | Trivial non-deleting destructor that writes `LodePNGState::vftable` to `this`. |
| `0x00448530-0x00448557` | `LodePNGState::ScalarDeletingDestructor` | Writes the same vtable pointer and calls operator delete when deletion flag bit `1` is set. |

## Evidence

- IDA lookup reports `0x00448520` as a `0x7` function and `0x00448530` as a `0x27` function.
- IDA decompilation of both methods shows only vtable reset plus optional delete in the scalar deleting destructor.
- The obtained LodePNG `20160501` header defines `LodePNGState` with a virtual destructor when compiled as C++, matching the presence of vtable/destructor glue in this binary.
- Wave3 active output emits the scalar deleting destructor in `class_LodePNGState.cpp`.
- Wave3 disabled output emits the ordinary destructor, with a note that it was excluded as trivial. It is still a real class method and should remain documented for exact range accounting.

## Ownership Decision

Keep both functions with [UID:00007E][LodePNGState](by-class/LodePNGState.md). The disabled ordinary destructor should not be treated as missing project code; it is compiler/library glue for the third-party LodePNG state object.
