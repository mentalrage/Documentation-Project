## Evidence

- Existing docs identify `ExceptionHandler` as a singleton top-level exception filter class.
- Live IDA MCP confirms all listed modeled function starts and end-exclusive ranges. The constructor has a caller from the application startup region at `0x00463e3a` inside `sub_4639D0`.
- IDA MCP confirms [UID:0000UG][DestroyExceptionHandler_4673A0](by-item/DestroyExceptionHandler_4673A0.md) at [UID:0000YW][0x004673a0-0x004673b1.DestroyExceptionHandler](by-memory/0x004673a0-0x004673b1.DestroyExceptionHandler.md) reads [UID:0000QN][g_pCrashTarget](by-global/g_pCrashTarget.md) and invokes the active handler through vtable slot 0 with delete flag `1`.
- [UID:00014F][0x004ab830-0x004ab86f.TopLevelExceptionFilter](by-memory/0x004ab830-0x004ab86f.TopLevelExceptionFilter.md) restores [UID:0000KJ][KeySpeedMgr](by-file/KeySpeedMgr.md) settings, checks byte `[g_pCrashTarget + 4]`, and calls the report helper only when that byte is not set.
- The report helper writes `BCrash.nfo`, emits version, exception code, fault address, registers, and stack data, and attempts `IMAGEHLP.DLL` symbol walking before falling back to frame-chain walking.
- [UID:00003A][Crasher](by-class/Crasher.md) writes byte `[g_pCrashTarget + 4]` before deliberately triggering a null write, tying it to this source family.
