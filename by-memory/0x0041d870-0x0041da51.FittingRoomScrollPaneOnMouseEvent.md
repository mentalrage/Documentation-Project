## Behavior

Handles mouse input for the fitting-room scrollbar. The method takes a mouse-event record whose event kind is stored at `event + 4`, with cursor coordinates at `event + 8` and `event + 12`.

Observed event behavior:

- Event kind `1` acts like mouse-down. The method checks whether the event point lies in the scrollbar pane rect, verifies that scrolling is enabled and the scrollable range is positive, then returns handled for an already-active part. If no part is active, it hit-tests the cursor; a no-part result is still treated as handled. A real part result captures mouse input, optionally prepares thumb drag state, stores the active part byte, calls [UID:0002D5][0x0041e8b0-0x0041e970.FittingRoomScrollPaneProcessActivePart](by-memory/0x0041e8b0-0x0041e970.FittingRoomScrollPaneProcessActivePart.md), starts a `200` millisecond repeat timer, invalidates the scrollbar, and sets the dragging/inside flag.
- Event kind `3` acts like mouse-up/cancel. It always clears the dragging/inside flag and invalidates the pane. If a scrollbar part is active, it also releases capture, stops the repeat timer, clears the active byte to `0xff`, invalidates and clears the previous hot part when present, and returns handled.
- Event kind `0` returns handled only when an active part is already present, and only then invalidates the pane.
- Other event kinds return not handled.

IDA decompilation names the receiver as `this`, but most object-field accesses subtract `0xa0` before accessing pane state. Treat this as a vtable/secondary-base dispatch artifact: the logical `FittingRoomScrollPane` base is `this - 0xa0` in the current decompiler output.
