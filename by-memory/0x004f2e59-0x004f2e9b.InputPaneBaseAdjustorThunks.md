## Interpretation

These six functions are the destructor entries used by secondary and tertiary vtable views in the reusable input-pane inheritance layout. The incoming `this` pointer is a subobject pointer at `+0xa0` or `+0xa4`; the thunk subtracts that offset and tail-jumps to the real scalar deleting destructor. No cleanup policy, UI behavior, or key-input behavior lives in these wrappers.

For source reconstruction, express this as normal virtual destructors on the C++ classes and let the compiler produce adjustor thunks as needed. Do not add explicit `AdjustorThunkDestructor` member functions to reconstructed project source.

`NumberInputPane`, `CharArgsInputPane`, `NumberArgsInputPane`, and `MultiLineInputPane` reuse the two LineInputPane-family adjustors in their secondary/tertiary destructor slots. That is vtable reuse, not proof of independent source-authored destructor bodies inside this range.

## Generated-Name Pollution And Rejected Alternatives

Current `simroot_v2` metadata propagates these thunk addresses into generated class method inventories and, for some classes, rewrites them as source-like destructor wrappers with incorrect member-field reasoning. Treat the IDA disassembly and vtable xrefs above as the authoritative interpretation.

Rejected generated names include `sub_4F2E59`-style raw labels and Ghidra/OOAnalyzer `virt_meth_0x4f2e59`, `virt_meth_0x4f2e64`, `virt_meth_0x4f2e6f`, `virt_meth_0x4f2e7a`, `virt_meth_0x4f2e85`, and `virt_meth_0x4f2e90`. Those labels identify vtable slots and analysis artifacts, not source methods that should be emitted.

Rejected split model: per-thunk source children would add bookkeeping but no source behavior. The six bodies are contiguous, uniform, compiler-generated, and share one vtable-family source route.

Rejected owner model: [UID:0000K7][InputPanes](by-file/InputPanes.md) and [UID:0001XS][InputPaneBaseVtableFamily](by-type/by-vtable/InputPaneBaseVtableFamily.md) explain why the compiler emits this range, but assigning this memory page to either owner would imply source-authored executable content. Keep this page ownerless and non-emitting.

## No-Code Proof

This target must not receive `RECONSTRUCTION_CPP CODE`.

1. The body of each function is only a base-subobject `this` adjustment plus a tail jump to an already documented scalar deleting destructor.
2. Source C++ should express normal class declarations and virtual destructors in `InputPanes.cpp`; MSVC will regenerate secondary/tertiary adjustor thunks from the inheritance layout.
3. Explicit source functions such as `LineInputPaneFamilySecondaryScalarDeletingDestructorAdjustorThunk()` would be decompiler-shaped ABI glue and would pollute final output.
4. `[[CHILDREN]]` is also wrong for this page because the target is not a source container; it is one ignored compiler artifact with no source-bearing children.
