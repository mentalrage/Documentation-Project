## Behavior

The effective binary signature is a `__thiscall` vector-header operation with two explicit arguments: insertion position and `const RankingRewardItem&`; it returns the inserted element pointer internally. The receiver is the three-pointer vector header at offsets `+0/+4/+8` for begin/end/capacity.

At the sole call site `0x0045dacd`, the parser loads the receiver from `RankingRewardEntry + 0x224`, passes the current end pointer as insertion position, and passes its stack-local item as the value. Entry offsets `+0x224/+0x228/+0x22c` are decimal 548/552/556 (Verified with `tools/int_convert.py`). The return value is unused. The parser's spare-capacity branch performs the same row copy inline, proving this target is only the full-capacity lowering of `items.push_back(item)`.

### RankingRewardItem Semantics

Each row is exactly `0x208` / 520 bytes (Verified with `tools/int_convert.py`): `wchar_t name[256]` at `+0x000`, 32-bit `quantity` at `+0x200` / 512, 16-bit `iconId` at `+0x204` / 516, `paletteIndex` at `+0x206` / 518, and one reserved/alignment byte at `+0x207` / 519 (all decimal conversions Verified with `tools/int_convert.py`).

The parser deliberately uses non-value-initialized `RankingRewardItem item;`. It writes the counted name and three scalar fields, then the fast path and this slow path copy all 520 bytes. Unused name-tail bytes and the final reserved byte may therefore retain stack data. No constructor, destructor, copy method, or per-element cleanup is called; `0x82` / 130 dwords are copied (Verified with `tools/int_convert.py`). [UID:0003X9][0x0045ef50-0x0045efd0.RankingRewardItemVectorClone](by-memory/0x0045ef50-0x0045efd0.RankingRewardItemVectorClone.md) independently uses raw contiguous memmove for the same rows.

### Count, Position, And Growth

The helper computes insertion index, old size, and old capacity from pointer spans divided by 520. Although the only source use passes `end()`, the binary supports an arbitrary insertion position.

If old size equals `0x7e07e0` / 8,259,552 items (Verified with `tools/int_convert.py`), it calls shared no-return `VectorTooLong_421500`, which reports `vector<T> too long`. Requested size is old size plus one. Capacity grows by capacity plus half when that value is safe and at least the requested size; otherwise it uses the requested size. This is observed MSVC/Dinkumware template policy, not a project-authored allocator rule.

### Allocation, Relocation, And Publication

Call `0x0045eb62` reaches [UID:0004J6][0x0045f290-0x0045f2f3.RankingRewardItemVectorAllocateStorage](by-memory/0x0045f290-0x0045f2f3.RankingRewardItemVectorAllocateStorage.md). It multiplies count by 520. Nonzero allocations below `0x1000` / 4096 bytes (Verified with `tools/int_convert.py`) use ordinary throwing `operator new`; zero count returns null. Large allocations request logical bytes plus `0x23` / 35 (Verified with `tools/int_convert.py`), align the usable pointer upward to `0x20` / 32 bytes, and store the raw allocation pointer at `aligned[-1]`. This caller performs the `0x7e07e0` vector maximum check first; UID0004J6 itself saturates oversized-count logical bytes to `UINT_MAX` and follows the large path rather than reporting vector length.

The inserted 520-byte row is copied into new storage before any old storage is moved or freed. End insertion memmoves the complete old used range. The generic non-end branch separately memmoves the prefix before the insertion point and suffix after the inserted row. Copy-before-free also preserves correctness if the supplied value aliases an old element, although the actual parser value is stack-local.

New begin/end/capacity are published only after allocation, row copy, range moves, and old-buffer release. New end is `newBegin + (oldSize + 1) * 0x208`, new capacity is `newBegin + newCapacity * 0x208`, and the returned pointer is `newBegin + insertIndex * 0x208`.

### Old-Storage Free And Validation

Deallocation size comes from the old capacity span, not only used size. Below the 4096-byte threshold, the vector begin pointer is passed to runtime free wrapper `sub_5C7526`. At or above the threshold, the helper loads the raw allocation pointer from `begin[-1]`, adds 35 to the logical capacity bytes, and validates `begin - rawBase - 4 <= 0x1f` / 31 (Verified with `tools/int_convert.py`). A failed check calls `__invalid_parameter_noinfo_noreturn`; otherwise the recovered raw pointer is freed. `sub_5C7526` is a broad wrapper over `j_j___free_base`, not a reward-local source API.

### Exception Behavior

There is no local EH funclet, item-destructor loop, or new-buffer cleanup call. Length failure and throwing allocation occur before vector publication, so the old triplet remains unchanged. After successful allocation, the full-row copy, memmoves, and trivial-buffer free do not throw; publication is last. This gives the source `push_back` strong pre-publication failure behavior for this trivial record. UID0003X7's explicit nested-vector deep-copy/EH cleanup is intentionally not projected onto this specialization.
