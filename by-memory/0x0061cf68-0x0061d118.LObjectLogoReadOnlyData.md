# 0x0061cf68-0x0061d118 LObject/Logo Read-Only Data

## Range

- Address range: `0x0061cf68-0x0061d118`
- Entity kind: `vtable/string-data`
- Disposition: reconstructable source-declared/generated-binary data.
- Rebuild handling: source class declarations, logo resource literals, and mail API string literals must be reconstructed; vtables are compiler-emitted.

## Summary

This `.rdata` span contains the `LObject` vtable, `LogoPane` and `LogoPlayerPane` vtables, a `PlainMemberFunctionObject0<LogoPane>` vtable, logo resource names, Bink error text, and MAPI mail DLL/procedure names. It ends at the `BaramApp` vtable.

## Evidence

- IDA MCP `py_eval` on 2026-05-28 reports named vtables for `LObject`, `LogoPane`, `LogoPlayerPane`, and the `LogoPane` callback object.
- IDA data xrefs tie the vtables and strings to executable code around `0x004f4a80`, `0x004f4c5a`, `0x004f53f7`, `0x004f5760`, `0x004f5838`, and `0x004f5b27`.
- The next named item at `0x0061d118` is `??_7BaramApp@@6B@`, which starts the application block.

## Reconstruction Notes

- `MAPI32.DLL` and `MAPISendMail` are dynamic API lookup strings and should be preserved as source literals in the mail/logon or startup-logo flow that uses them.
- `LogoPane` callback object data is compiler-generated from source callback binding; reconstruct the callback relationship in source rather than hand-porting a synthetic table.
