# 0x0066dd60-0x0066dd78 Image Extension Pointer Table

## Summary

- Address range: `0x0066dd60-0x0066dd78`
- Entity kind: initialized pointer table plus trailing padding
- Disposition: reconstructable project data
- Rebuild handling: profile-sidecar static pointer table
- Confidence: strong for pointer targets, consumer loop, and boundaries; medium for final table symbol name
- Parent attachment: attached to [UID:0000MS][ProfileStorage](by-file/ProfileStorage.md), whose current confidence is `80`.
- Reconstruction note: C++ intentionally left blank because the final table symbol name and source placement remain below the 95/95 gate.

This range contains a five-entry pointer table for profile image sidecar extension strings, followed by four zero bytes before the MapPane day/night float table. The profile sidecar refresh body uses the table as an indexed list of suffixes while probing user image sidecars under the NexusTK user directory.

## Layout

| `0x0066dd60` | `0x0061e964` | `bmp` | First extension probed by the sidecar search loop. |
| `0x0066dd64` | `0x0061e96c` | `pcx` | Second extension. |
| `0x0066dd68` | `0x0061e974` | `jpg` | Third extension. |

## Evidence

- Live IDA pointer inspection resolves the five entries to the wide strings `bmp`, `pcx`, `jpg`, `jpeg`, and `pnm`.
- Live `xrefs_to 0x0066dd60` reports one direct table-base ref at `0x005064d0` inside the modeled `0x005063e0-0x00506962` profile sidecar refresh body.
- Live `xrefs_to` for `0x0066dd64`, `0x0066dd68`, `0x0066dd6c`, `0x0066dd70`, and `0x0066dd74` reports no direct refs, matching indexed access from the table base.
- The consumer loop initializes the table offset to zero, pushes the pointer at `0x0066dd60 + offset`, formats `%s/%s.%s`, checks file existence, increments the offset by four bytes on misses, and stops after `0x14` bytes, which proves the five-entry count.
- The same profile sidecar body creates `Documents\\NexusTK\\users`, probes the extension list, then falls back through `.jpf` profile sidecar paths before publishing the loaded/empty profile data.
- The previous page [UID:00027O][0x0066dd50-0x0066dd60.MapObjectDirectionMasks](by-memory/0x0066dd50-0x0066dd60.MapObjectDirectionMasks.md) ends exactly at the first pointer. The next page [UID:00027Q][0x0066dd78-0x0066ddd8.MapPaneDayNightFloatTable](by-memory/0x0066dd78-0x0066ddd8.MapPaneDayNightFloatTable.md) begins exactly after the four-byte zero padding and has separate MapPane day/night refs.

## Reconstruction Notes

- Do not duplicate the string literals in unrelated image writer code unless a later caller proves the table is shared more broadly.
- Preserve the separate four-byte zero padding at `0x0066dd74-0x0066dd78`; it is not a sixth pointer and has no live xrefs.
- Keep ownership with [UID:0000MS][ProfileStorage](by-file/ProfileStorage.md) because the only live consumer is the profile sidecar refresh body, not MapPane or generic image writer code.
