## Behavior

This helper island mirrors the opcode `0x43` subtype handling in [UID:00021C][0x00484f70-0x0048540b.ClanStatusPacketDispatcher](by-memory/0x00484f70-0x0048540b.ClanStatusPacketDispatcher.md). The first, second, and sixth functions are directly called by the dispatcher:

- `0x00484fdb -> 0x004877d0`
- `0x00484fec -> 0x004879e0`
- `0x00485181 -> 0x00487ea0`

The remaining sibling functions have no IDA code or data xrefs, but they are byte-for-byte coherent dialog-opening helpers for the same packet subtype sequence. They likely represent retained source functions or generated helper variants from the same original Clan module, even if the active dispatcher inlines equivalent logic for cases `3-5` and `7-12`.

The dialog openers all use the same shape:

1. Initialize packet text decoding via `sub_516030`.
2. Check `packet[2]` for action/state.
3. Allocate either a one-field name dialog (`0x26c` bytes), a multi-field attribute dialog (`0x870` bytes), or an item dialog.
4. Call the shared base constructor (`0x00488b40`, `0x00489600`, `0x0048a1c0`, or `0x0048a810`) and install the derived Clan dialog vtables.

## Source Reconstruction Notes

Do not treat the no-xref sibling helpers as dead padding. They are valid function bodies and should remain source-authored until a stronger linker/object-layout explanation proves they are unreachable generated artifacts.

The final C++ should probably name the directly used handlers as `ClanStatusPane`/`ClanEnlistInputDialog` packet handlers, and keep the dialog opener siblings as file-local helpers or static member helpers in `Clan.cpp` until original naming is recovered.
