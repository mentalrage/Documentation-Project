## Field Meaning

The field at `this + 0x94` is best named `m_usesSoftwareBuffer`.

Evidence:
- `GrafPort::GrafPort` initializes `[this+0x94]` to `0`.
- This helper writes `1` to `[this+0x94]`.
- `GrafPort::UpdateRenderRegion` takes the DirectDraw surface allocation path when the byte is false and takes the software heap-buffer path when the byte is true.
- The software path allocates/frees the buffer at `this + 0x98` and stores row stride/pitch at `this + 0x9c`.
- Cleanup/destructor paths check `+0x94` before freeing `+0x98`.
- Surface paint/blit helpers check `+0x94` to select DirectDraw surface behavior versus software-buffer behavior.

Rejected names:
- `m_dirtyFlag` / `MarkDirtyFlag`: rejected because dirty/exposed state is represented by Region objects and invalidation helpers, not this byte. Setting this byte does not mark a rectangle dirty.
- `m_ownsSoftwareBuffer`: partly true but less precise. The byte gates use of the software backing path and also controls release of the owned heap buffer. `m_usesSoftwareBuffer` best matches all call sites.
- DirectDraw lock-state flag: rejected because DirectDraw behavior occurs when the byte is false, and lock-state/surface fields are separate.

## Caller Evidence

- IDA MCP `decompile 0x004b8be0` returns a two-line thiscall body equivalent to `this[148] = 1`.
- IDA MCP `xrefs_to 0x004b8be0` reports one direct caller at `0x00468411` inside `sub_4682C0`.
- The caller allocates/constructs a GrafPort, stores it in the owning object, calls this helper, and then continues pane/render setup. This is consistent with configuring that GrafPort for software backing, not with marking an already-rendered region dirty.
