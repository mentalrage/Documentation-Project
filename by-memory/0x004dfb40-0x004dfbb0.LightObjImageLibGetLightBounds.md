# 0x004dfb40-0x004dfbb0 LightObjImageLib Get Light Bounds

## Status

- Owner class: [UID:000076][LightObjImageLib](by-class/LightObjImageLib.md).
- Likely source file: [UID:0000KP][LightObjImageLib](by-file/LightObjImageLib.md).
- Entity kind: method/helper.
- IDA function: `sub_4DFB40`, exact function bounds `0x004dfb40-0x004dfbb0`.
- Rebuild handling: source-authored NexusTK project code.

## Behavior

This helper selects a [UID:0001UW][LightInfo](by-type/by-struct/LightInfo.md) record by index, falls back to the embedded default record at `this + 0x14` when the index is out of range, and writes a rectangle describing the light frame's local bounds.

When the selected record has a generated frame pointer at `LightInfo + 0x18`, the output rectangle is:

```text
left   = -radiusX
top    = -radiusY
right  =  radiusX + 1
bottom =  radiusY + 1
```

If the selected record has no generated frame, the helper writes an empty `0,0,0,0` rectangle. IDA shows the rectangle write is delegated to `sub_4B7C50`, the shared four-integer rectangle setter used throughout the client.

## Evidence

- IDA MCP decompilation shows `this[2]` as the count, `this[3]` as the entry buffer, `28 * index` as the row stride, and `this + 5` as the fallback record pointer.
- IDA disassembly confirms the function copies the first 0x18 bytes of the selected record to the stack, checks the frame pointer at `+0x18`, negates `radiusX`/`radiusY`, increments positive extents, and calls `sub_4B7C50(outRect, left, top, right, bottom)`.
- IDA xrefs report a caller at `0x0053c82b` inside `sub_53C810`, an external consumer of the light-library bounds helper.

## Boundaries

The raw ordinary destructor ends before the alignment padding at `0x004dfb36-0x004dfb40`; this helper starts at `0x004dfb40` and ends at `0x004dfbb0`, immediately before `DrawLightMode1`.

## Caveats

The behavior is clear, but the final source-level name is still inferred from the rectangle output semantics and its LightInfo field usage. Keep the name as a documentation label until caller-side ownership at `0x0053c810` is fully documented.
