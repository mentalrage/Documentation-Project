## Behavior

The helper takes a mutable unsigned 16-bit pixel buffer and a signed `int pixelCount`. Its entry tests `pixelCount` and returns before loading or dereferencing `pixels` when the count is zero. For a positive count `N`, it rewrites exactly `N` consecutive 16-bit words in place at a two-byte stride. The complete source draft exists only in the managed formal C++ header above.

The exact observed expression is `(pixel & 0x001f) | ((pixel >> 1) & 0x7ff0)`. It is not a canonical RGB565-to-RGB555 mask and must not be cleaned up to `0x7fe0`: source red bits 15..11 become destination 14..10, source green bits 10..6 become destination 9..5, source green bit 5 becomes destination bit 4, source blue bits 4..0 are preserved, and destination bit 4 is therefore the OR of source green bit 5 and source blue bit 4. Destination bit 15 is clear. This produces the following checked edge values:

| Source | Destination | Relevant observation |
| --- | --- | --- |
| `0x0000` | `0x0000` | zero remains zero |
| `0xffff` | `0x7fff` | destination bit 15 is cleared |
| `0xf800` | `0x7c00` | red shifts into RGB555 position |
| `0x07e0` | `0x03f0` | full six-bit green includes destination bit 4 |
| `0x001f` | `0x001f` | low five blue bits are preserved |
| `0x0020` | `0x0010` | source green LSB alone sets destination bit 4 |
| `0x0010` | `0x0010` | source blue MSB alone sets destination bit 4 |
| `0x0030` | `0x0010` | the two inputs OR-fold rather than add |

The machine loop decrements on nonzero rather than testing `> 0`. A negative `pixelCount` is outside the valid caller contract and would count down through its unsigned 32-bit residue until zero while advancing the pointer, so the documentation records the nonnegative precondition without adding a guard or hardening the source. The binary also has no null-pointer, dimension, multiplication-overflow, or storage validation; zero is safe without pointer use, while a positive count requires valid storage.

In the only known caller, [UID:000200][0x00458560-0x00458585.EPFTileContextNormalizePostDecodePixels](by-memory/0x00458560-0x00458585.EPFTileContextNormalizePostDecodePixels.md), the call is gated by `!g_surfaceUsesRgb565Pixels` / raw `byte_69B3D5`. JPF at `0x004d07b0` and raw JPEG at `0x004d0a90` build RGB565 words with `B >> 3 | 8 * (G & 0xfc | 32 * (R & 0xf8))`; PNG at `0x004d0d90` uses the same primary-pixel pack plus a separate alpha plane; ZPF/FPF at `0x004d05f0` copies `2 * width * height` source bytes before normalization. Surface initialization sets the D5 flag for 32-bit output and for 16-bit output with green mask `0x07e0`, while 24-bit and RGB555-compatible paths clear it. The producer and flag evidence therefore establishes RGB565 input followed by this exact compatibility transform on the non-RGB565 Surface path.
