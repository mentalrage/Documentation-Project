# 0x0060f4c0-0x006104f4 LodePNG Read-Only Data

## Summary

- Address range: `0x0060f4c0-0x006104f4`
- Entity kind: third-party LodePNG read-only data
- Disposition: mostly reconstructable static third-party embed data; current tail also contains shared literal-pool constants and the next MiniMap RTTI boundary dword
- Rebuild handling: `third-party/runtime` for the LodePNG-owned bytes, with `source-declared/generated-binary` caveats for shared tail constants
- Confidence: strong

This span contains the LodePNG version/date literal, LodePNG state vtables, PNG chunk-name constants, and a dense block of LodePNG/zlib/PNG error strings. A 2026-06-07 IDA MCP review also shows that the final bytes after the last LodePNG error string are not purely LodePNG-owned: `0x006104ac-0x006104ef` is a shared literal-pool tail referenced by both LodePNG and non-LodePNG UI/render code, and `0x006104f0` is the RTTI locator immediately before the next MiniMap vtable at `0x006104f4`.

- IDA string names and contents in this span match LodePNG chunk tags and error messages.

## Rebuild Notes

Do not recreate the LodePNG strings or vtables as NexusTK source. Include the matched LodePNG static embed/source and allow the compiler to regenerate this data. Treat the shared literal-pool tail as compiler/linker-emitted constants produced by whichever source files use matching literals; it is not a reason to hand-port raw `.rdata` bytes into LodePNG.
