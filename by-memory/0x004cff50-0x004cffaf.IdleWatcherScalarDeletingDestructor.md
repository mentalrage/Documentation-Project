# 0x004cff50-0x004cffaf IdleWatcher Scalar Deleting Destructor

## Status

- Exact compiler-only child split from [UID:000171][0x004cfe60-0x004cffaf.IdleWatcher](by-memory/0x004cfe60-0x004cffaf.IdleWatcher.md).
- `CANONICAL_OWNER:NONE`, `RECONSTRUCTABLE:FALSE`, blank emitter/position/formal C++, and `Nested:-8` are intentional.
- [UID:00006C][IdleWatcher](by-class/IdleWatcher.md) owns the virtual destructor declaration, but this delete-flag wrapper is not a human-authored method.

## Exact Machine Behavior

- Accepts the compiler deleting-destructor flag word and preserves the complete-object address as its return value.
- Restores the primary IdleWatcher vptr and the EventHandler/TimerHandler secondary views before teardown.
- Clears [UID:0002VY][0x0069af1c-0x0069af20.g_pIdleWatcher](by-memory/0x0069af1c-0x0069af20.g_pIdleWatcher.md) at `0x004cff70`, the inlined `Singleton<IdleWatcher>` base-destructor effect.
- Invokes ordinary Pane/base teardown on the complete object.
- Tests flag bit `1` for normal storage release through the project operator-delete wrapper at `0x004f4ac0`.
- Handles the guarded/size-aware flag route using complete object size `0x100` when bit `4` participates in the compiler ABI path.
- Returns the original complete-object pointer and ends with `retn 4`.

## Reachability And Vtable Routes

- Primary IdleWatcher vtable slot `0x0061b56c` points directly to this function.
- [UID:0004LI][0x004cff37-0x004cff4d.IdleWatcherDestructorAdjustorThunks](by-memory/0x004cff37-0x004cff4d.IdleWatcherDestructorAdjustorThunks.md) jump here after correcting EventHandler `this - 0xa0` and TimerHandler `this - 0xa4` receivers.
- Application shutdown loads `g_pIdleWatcher` at `0x004f6652` and invokes the primary virtual deleting-destructor slot with flag `1`, corresponding to source `delete g_pIdleWatcher`.
- No ordinary source caller targets `0x004cff50` directly; the function is reached through virtual/compiler deletion routes.

## Compiler-vs-Source Disposition

- The virtual declaration and empty ordinary `IdleWatcher::~IdleWatcher()` body are sufficient source to regenerate derived vptr restoration, Singleton clear, Pane teardown, delete-flag handling, adjustors, storage release, and return-this ABI.
- Emitting this body manually would duplicate the compiler's destructor protocol and could clear the singleton, tear down Pane, or free storage twice.
- The guarded object-size route is ABI/compiler evidence for the exact `0x100` layout, not a source-level overload that should be reconstructed here.

## Boundaries And Negative Evidence

- IDA models `0x004cff50`, size `0x5f`, exact half-open range `0x004cff50-0x004cffaf`.
- Preceding `0x004cff4d-0x004cff50` is three bytes of `0xcc` alignment after the adjustor pair.
- Bytes `0x004cffac-0x004cffae` are terminal `C2 04 00`; existing `0x004cffaf-0x004cffb0` is one `0xcc` byte before ImageLib code.
- No source-owned state transition, timer operation, callback, or independent semantic method exists in this range.
- Historical descriptions that treated scalar deletion as a source method or folded it into the ordinary destructor are superseded. It must not receive owner/emitter UID00006C or appear in generated `IdleWatcher.cpp`.
