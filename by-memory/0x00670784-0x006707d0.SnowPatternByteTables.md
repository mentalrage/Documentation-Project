## Evidence

- IDA MCP `py_eval` confirms `SnowingLayerPane::RandomizeSnowParticles` at `0x005c1f50` references threshold data at `0x00670785` and size offsets at `0x00670788`.
- IDA MCP `py_eval` confirms `SnowingLayerPane::RenderSnowParticles` at `0x005c20e0` references pattern data at `0x0067078c` and `0x0067079c`.
- IDA MCP `py_eval` confirms `SnowingLayerPane::UpdateAndRenderSnowParticles` at `0x005c1c80` references alternate threshold/size data at `0x006707ad` and `0x006707b0`, and pattern data at `0x006707b4` and `0x006707c4`.
- Raw bytes at `0x006707d0` begin the ASCII string `Bogus message code %d`, so this snow byte-data block should not extend past `0x006707d0`.
- 2026-05-31 IDA MCP `lookup_funcs` confirms the modeled users at `0x005c1c80`, `0x005c1f50`, and `0x005c20e0`.
- 2026-05-31 IDA MCP `xrefs_to` confirms the documented threshold, size-offset, and pattern start addresses are referenced from those snow functions.
- 2026-05-31 IDA MCP `decompile` confirms the threshold loops read `*(ptr - 1)` and `*ptr`, which is why `0x00670784` is the lower sentinel even though the direct xref lands at `0x00670785`.
- 2026-05-31 IDA MCP `get_bytes` confirms `0x00670784-0x006707d0` contains two threshold/size/pattern sets, and `0x006707d0` is followed by padding plus the unrelated `Bogus message code %d` string.

## Data Caveats

The first threshold loop uses a pointer to `0x00670785` and reads `threshold[-1]`, so the byte at `0x00670784` is documented as a sentinel even though the direct xref lands at `0x00670785`. Keep that detail visible when rebuilding the source declarations.
