# 0x0067a7c8-0x0067a7cc g_pConfig

## Summary

- Address range: `0x0067a7c8-0x0067a7cc`
- Entity kind: global pointer
- Proposed name: `g_pConfig`
- Disposition: reconstructable NexusTK global data
- Confidence: strong for address and broad config-object role

This four-byte zero-initialized global stores the active `Config` / `RegistryConfig` object pointer. It is one of the most widely referenced process globals, with hundreds of IDA xrefs from UI, profile, network, audio, and packet-handling code.

## Layout

| Range | Current IDA name | Proposed source form |
| --- | --- | --- |
| `0x0067a7c8-0x0067a7cc` | `dword_67A7C8` | `Config *g_pConfig;` or `RegistryConfig *g_pConfig` at sites that require the derived layout. |

## Evidence

- IDA MCP reports four zero-initialized `.data` bytes and 433 direct data xrefs to `0x0067a7c8`.
- [UID:000031][Config](by-class/Config.md) documents `Config::Config` installing `g_pConfig` and the deleting destructor clearing it.
- [UID:000110][0x0048e480-0x0048f3f1.ConfigAndRegistryDefaults](by-memory/0x0048e480-0x0048f3f1.ConfigAndRegistryDefaults.md) covers the config constructor/default initialization body.
- Existing pane and profile docs consistently resolve generated names such as `g_powerThresholdConfig` to `dword_67A7C8` field offsets rather than separate globals.

## Reconstruction Notes

Treat `dword_67A7C8` as the canonical config pointer until the final type split between `Config` and `RegistryConfig` is recovered. Rename generated aliases that imply separate globals once evidence shows they are `g_pConfig` field accesses.
