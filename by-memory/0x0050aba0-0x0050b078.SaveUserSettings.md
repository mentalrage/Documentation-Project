The function writes the same profile layout consumed by `LoadUserProfileData`: fixed wide-string groups, simple wide-string objects, the dynamic string vector, compact shortcuts, 30 [UID:0001V1][MacroHotkeyRecord](by-type/by-struct/MacroHotkeyRecord.md) rows, and trailing flag pairs.

The 2026-06-07 IDA boundary recheck reports `sub_50ABA0` as `0x0050aba0-0x0050b078`, with no function at the exclusive end and eight `0xcc` padding bytes before the next function at `0x0050b080`. This keeps the page from absorbing the following routine.

The same recheck finds eight code references to `0x0050aba0`: `0x00504850` in `sub_5047F0`, a raw/no-function callsite at `0x0053dd8c`, and calls inside `sub_53DDB0`, `sub_53ECF0`, `sub_53F0A0`, `sub_53F830`, `sub_541FA0`, and `sub_5424B0`. That spread supports a shared profile-storage helper rather than ownership by one dialog class.

IDA data/call evidence ties the routine to the user profile file path and writer helpers: it reads `g_pConfig` storage at `0x0067a7c8`, calls `SHGetFolderPathW`, formats/creates `%s\NexusTK` and `%s\NexusTK\users`, formats `%s/%s.usr`, calls directory/file helper pointers at `dword_69BE5C`, `dword_69BECC`, `dword_69BE60`, and `dword_69BE14`, then emits the serialized blocks through repeated `_fwrite`/`_fputwc` calls before `_fclose`.
