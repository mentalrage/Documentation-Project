## Behavior

The receiver is the three-pointer `std::vector<RankingRewardEntry>` state. A null begin pointer is already the all-null empty state and returns without mutation. For a non-null allocation, the helper walks `[begin,end)` in exact `0x230` / 560-byte entry strides. At every live entry it invokes [UID:0004J4][0x0045f160-0x0045f1c6.RankingRewardItemVectorDestroy](by-memory/0x0045f160-0x0045f1c6.RankingRewardItemVectorDestroy.md) on entry `+0x224` / 548, matching the accepted `RankingRewardItemVector items` member at `+0x224/+0x228/+0x22c`.

After every live entry's nested vector is destroyed, the helper computes outer allocation bytes from `capacity - begin` using the `0x230` stride, frees the outer storage, and writes zero to begin, end, and capacity. The scalar deleting destructor supplies this receiver as complete dialog object `+0x26c`, matching `m_rewardEntries` at `+0x26c/+0x270/+0x274` and complete object size `0x278`.

`RankingRewardItem` rows are `0x208` / 520 bytes and have no nontrivial member destructor. Consequently UID0004J4 frees item-vector capacity storage directly without a per-row destructor loop, validates aligned metadata when required, and clears the nested triplet. This is consistent with the parser, UID0003X6 relocation, and UID0003X9 contiguous copy behavior.

## Allocation And Termination Semantics

- Capacity storage bytes, not occupied bytes, control deallocation size. The reciprocal multiply/divide sequence derives capacity count from `(capacity - begin) / 0x230` and multiplies back by `0x230`.
- Logical capacity bytes below `0x1000` free the ordinary begin pointer.
- At or above `0x1000`, the helper adds `0x23` to the logical size passed to free, reads the raw allocation pointer from the dword before the aligned begin pointer, and requires `aligned - raw - 4 <= 0x1f`.
- Invalid large-allocation metadata calls `_invalid_parameter_noinfo_noreturn`. This is a terminating runtime guard, not a recoverable exception or ranking-domain branch.
- Normal nested and outer deallocation has no local catch, cleanup registration, or recoverable throw path. Successful cleanup clears all three outer vector pointers.
- These allocator details are preserved as binary evidence. Human source should retain ordinary typed vectors and let the compiler/library regenerate the checked allocation policy rather than exposing it as a project helper API.
