## Signature And Return Shape

- Calling convention: ordinary internal helper with no explicit stack arguments.
- Return value: `0` when the stream is opened/primed, `1` for most WinMM/document-load/property/setup failures after normal cleanup, and `-1` when a newly allocated MIDI buffer cannot be locked.
- IDA still names the function `sub_525920`; the page name describes its stream-open and two-buffer priming behavior.

## Behavior

This helper opens the WinMM MIDI stream and primes the two-buffer playback queue.

Live IDA MCP decompilation and disassembly show this sequence:

| Step | Address | Behavior |
| --- | --- | --- |
| Open stream | `0x0052592b-0x00525952` | If `hms` is null, calls `midiStreamOpen(&hms, &puDeviceID, 1, 0x00525be0, 0, 0x30000)`. The callback pointer is [UID:0001CG][0x00525be0-0x00525dbb.MidiStreamCallback](by-memory/0x00525be0-0x00525dbb.MidiStreamCallback.md). |
| Allocate two headers | `0x00525958-0x00525991` | Iterates over two `0x54`-byte `MIDIHDR` slots, sets `dwBufferLength = 0x400`, allocates `0x400` bytes with `GlobalAlloc(0x42, 0x400)`, locks the block, and stores the data pointer in `pmh.lpData`. |
| Open/parse MIDI document | `0x00525993-0x005259a4` | Calls [UID:0002C5][0x005270c0-0x005270d5.MidiParseSuccessWrapper](by-memory/0x005270c0-0x005270d5.MidiParseSuccessWrapper.md) for static document state `0x0069b828` and the selected `Destination` path. |
| Initialize stream state | `0x005259aa-0x005259eb` | Copies time division from `0x0069b82c`, copies four lanes of default channel/volume data from `0x0061fb60` into `0x0069b5d0-0x0069b600`, sets property data to `8`, and calls `midiStreamProperty(hms, propdata, 0x80000001)`. |
| Prime buffers | `0x005259f9-0x00525aca` | Initializes active queue counters, clears per-header status fields, fills one or two buffers through [UID:00023C][0x005271b0-0x005277bb.MidiSMFLoadAndStreamFillHelpers](by-memory/0x005271b0-0x005277bb.MidiSMFLoadAndStreamFillHelpers.md), records byte counts, prepares unprepared headers with `midiOutPrepareHeader`, and submits them with `midiStreamOut`. |
| End-of-file handling | `0x00525a56-0x00525a63` | Treats fill return `0xffffff99` as the no-more-data condition and stops after queuing the current buffer. Other non-zero fill results take the cleanup/failure path. |
| Success state | `0x00525ad0-0x00525ade` | Sets the stream-prepared/running flag at `0x0069b520`, resets the active buffer index at `0x0069b610`, and returns `0`. |
| Cleanup failure path | `0x00525aed-0x00525af7` | Calls [UID:0001CI][0x005270e0-0x005271a3.MidiDocumentRelease](by-memory/0x005270e0-0x005271a3.MidiDocumentRelease.md), then returns `1`. |
| Allocation failure path | `0x00525b03-0x00525b0c` | Returns `-1` when a GlobalAlloc/GlobalLock buffer pointer is null. |

## Reconstruction Notes

This is private WinMM startup logic. Keep it with the `MidiPlayer` source family and model it as `OpenMidiStream` / `PrimeMidiBuffers` until a better original name is recovered.

The helper should remain separate from [UID:0001CG][0x00525be0-0x00525dbb.MidiStreamCallback](by-memory/0x00525be0-0x00525dbb.MidiStreamCallback.md): it installs the callback pointer and primes buffers, while the callback handles asynchronous buffer returns and refills.

C++ remains blank because final source still depends on stable WinMM state/global names, MIDI document type names, and helper return constant naming.
