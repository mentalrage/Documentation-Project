## Heuristic / Inference Reanalysis And Validation

`DestroyKeySpeedMgr` is a high-probability original-style name, not merely a descriptive convenience. It matches neighboring file-local cleanup names such as `DestroyDATFileMgr` and `DestroyExceptionHandler`, has exactly one WinMain call, and expresses the body without exposing deleting-destructor ABI mechanics. Its source return type is `void`: the caller ignores EAX, the null path leaves EAX undefined, and source `delete` has no meaningful return.

Direct literals are more plausible than five file-scope constants. The binary has five pooled strings with one use each, all inside WinMain, and no standalone declaration/pointer table. Replacing the `k*` identifiers with literals makes the source self-contained and naturally regenerates pooled `.rdata` without inventing unobserved declarations.

The exact constructor argument order is `BaramApp app(hInstance, L"Nexon", L"NexusTK")`: assembly pushes the application title at `0x004f5cbf`, publisher at `0x004f5cc4`, then `hInstance` for the call. Right-to-left calling convention therefore gives constructor parameters `hInstance`, publisher, title.

The PlatformApi route remains Unicode despite the ANSI shell structure. `0x0069be70` is installed from `GetCurrentDirectoryW`, accepts `(DWORD, LPWSTR)`, and is used by eleven wide-path consumers. The observed source then stores that WCHAR buffer into `SHELLEXECUTEINFOA.lpDirectory` and calls `ShellExecuteExA`. Correct reconstruction preserves this oddity rather than silently changing either API family. The source-facing closure is exact: UID0002AS adds `extern DWORD (WINAPI *g_pfnGetCurrentDirectoryW)(DWORD bufferLength, LPWSTR buffer);` to `PlatformApi.h` with `<windows.h>`, and WinMain includes that provider header; a WinMain-local extern or ANSI substitute is rejected.

StartupWindow provider inference is now closed from the same accepted class-specific Singleton policy used by DirectX, ThreadMan, MiscWorkThread, and other modules. RTTI proves a non-virtual empty `Singleton<StartupWindow>` base at `+4`, and the constructor's `lea this+4`, adjusted-null publication, and subtraction by four are the inlined `Singleton<StartupWindow>::Singleton()` specialization, not a handwritten `g_pStartupWindow = this` statement. The unconditional store at the end of the ordinary destructor and the corresponding scalar-wrapper store are the inlined reverse-base `Singleton<StartupWindow>::~Singleton()` specialization, so the derived destructor source must not duplicate `g_pStartupWindow = NULL`. The 0x58 layout then follows exactly: vptr `+0`, empty-base address and `m_assetsLoaded` `+4`, `m_instance +8`, `m_noticeWindow +0xc`, `m_backgroundImage +0x10`, two 0x20 `StartupNoticeButton` records at `+0x14/+0x34`, and `m_resultReady +0x54`. The constructor's four derived assignments belong in its body, not an initializer list, because the exact binary order after base publication/vptr installation is global flag, instance, loaded flag, result flag. The loader's physical stores reject separate `m_start*`/`m_exit*` members and resolve the second record's three image slots as normal/null/pressed.
