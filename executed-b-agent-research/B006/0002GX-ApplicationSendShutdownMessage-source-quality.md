## Heuristic And Inference Reanalysis

### Message Object Layout

The `Message` class docs and MessageCore MCP facts show the constructed object is three dwords at source level:

- dword `+0`: vtable/base object state
- dword `+4`: `MessageType m_type`
- dword `+8`: `SortedList *m_entries`

The target's local stack allocation is larger because of compiler EH bookkeeping. Hex-Rays groups adjacent stack storage into `_DWORD v2[6]`, but only the first three dwords are the `Message` object constructed by `sub_520E30`.

### EH State Versus Payload Clear

The write at `0x00467998` should not be modeled as application source.

Positive evidence:

- The instruction writes `[ebp+var_4]`, the standard compiler EH state slot in this frame.
- It appears immediately after the constructor succeeds.
- The target has an EH cleanup chunk that destructs the local `Message` on unwind.
- The explicit normal destructor call at `0x004679aa` matches ordinary automatic-object scope exit.
- No support constructor/destructor/consumer evidence shows a fourth, fifth, or sixth source-level `Message` payload field.

Negative evidence against payload/source-field interpretation:

- ChangeMan consumers read the message type at `message + 4`, not any payload slot at `message + 20`.
- The `Message` constructor initializes only the vtable/type/list dwords.
- No listener checked reads a target-specific payload after this send.
- Treating `v2[5] = 0` as source would duplicate compiler EH state in reconstructed C++ and would overfit Hex-Rays' local-array artifact.

Recommended target wording should explicitly preserve this correction so the old "payload/status clear" reading does not return.
