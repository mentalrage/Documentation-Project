## Heuristic / Inference Reanalysis And Validation

1. **Constructor ABI and parameters.** MCP decompiles `_DWORD *__thiscall sub_46AA40(_DWORD *this, int a2, OLECHAR *a3, int a4, int a5)`, and disassembly ends in `retn 10h`. The first explicit argument is never read; both callers pass zero. The second is forwarded without writes into BrowserControlPane construction, and callers supply a packet-derived wide URL or literal `L"help.nexustk.com/wiki"`. The final two arguments become width/height with zero selecting defaults. Best source definition: `BrowserDialog::BrowserDialog(int, const OLECHAR *initialUrl, int width, int height)`. Naming the first argument `controlId`, `mode`, or `flags` is rejected because current evidence proves only type, position, non-use, and caller value zero.
2. **Base construction and inheritance.** The body invokes the DialogPane base constructor with `L""`, `-1`, and `true`, then installs three BrowserPane views before singleton publication and three BrowserDialog views afterward. Current BrowserPane/WebBoard precedent supports source shape `BrowserPane(L"", -1, true)`. RTTI independently proves `Singleton<BrowserDialog>` as a non-virtual base. Direct DialogPane calls and vptr writes are compiler lowering of base/derived construction, not source statements.
3. **Singleton publication.** At `0x0046aaa0`, code forms `this+0x278`, converts it back to complete-object `this`, and stores it in `g_pBrowserDialog` at `0x0046aab7`, with a theoretical null-base fallback clear at `0x0046aabe`. RTTI base descriptor `0x00642f14` has `mdisp=0x278`, `pdisp=-1`, `vdisp=0`. This is best represented by `Singleton<BrowserDialog>()` base initialization, not raw pointer arithmetic.
4. **Constructor EH.** Disassembly includes 261 instructions across the main body and far EH funclets. Action `0x005fac2b -> 0x0046a8a0` destroys the completed BrowserPane base; action `0x005fac33`, after adding `+0x278`, jumps at `0x005fac3c` to the singleton-clear thunk `0x00470220`; actions `0x005fac41`, `4c`, `57`, and `62` free failed child allocations; `0x005fac6d` is the SEH handler. These are generated from base/member construction and `new`, and must not appear in formal source.
5. **Field layout.** Caller allocations are `640` bytes (`0x280`). `this[155]` is offset `+0x26c`; both branches assign a returned `0x338`-byte BrowserControlPane allocation to it and later consumers dereference it. It is a pointer field. `this[158]`/`+0x278` stores effective width; `this[159]`/`+0x27c` stores effective height. The `Singleton` empty base overlaps `m_width` at `+0x278` through EBO. No title-button member store exists; the button is a local registered with DialogPane.
6. **Dimension defaults.** Nonzero width/height are retained. Zero width becomes `662` (`0x296`), and zero height becomes `562` (`0x232`). The current-layout centering calculation deliberately uses fixed `1024x768`; the legacy branch deliberately uses signed global screen dimensions `g_screenWidth`/`g_screenHeight`.
