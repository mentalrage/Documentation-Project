## Heuristic / Inference Reanalysis And Validation

1. Aggregate liveness and source role: UID00011M contains three exact modeled methods separated by `0xcc` padding. It is a useful index but has no additional source body. Keeping it reconstructable with the class emitter causes a duplicate Empty Emitter Marker. Reclassifying only the aggregate as non-reconstructable/non-emitting does not discard any source and does not clear semantic ownership: UID00009M remains `CANONICAL_OWNER` because every exact in-range method belongs to `NumericStringControlPane`.
2. Constructor ABI: `sub_499910` is a `__thiscall` constructor taking `const wchar_t *`, `int`, `char`, and `const RectBounds *`; the two callers push these exact argument widths/order and allocate `0x118`. The decompiler's final `int *a5` is the rectangle pointer reused as dead stack storage after base construction, not the real source type.
3. String member: `+0x108` is one pointer wide. Calls to `InitializeEmptyWide`, `AssignWideLiteral`, destructor release, and `c_str` identify `mystr::StringBase<wchar_t, mystr::mychar_traits<wchar_t> >`, not the larger `SimpleUString`/SSO representation.
4. Loader out-size alias: the constructor passes a writable stack address to `LoadDatFileBuffer`; the result is never read. The plausible human source declares a local `int glyphBufferSize` and passes its address. Passing `NULL` is rejected because the binary passes non-null; using `&bounds` is rejected as decompiler stack-slot reuse.
5. Resource ownership/failure: `LoadDatFileBuffer(L"9X11FONT.BIN", 99, &glyphBufferSize)` supplies `m_numericGlyphs`. There is no constructor null check, exception recovery, or fallback allocation in the target; the destructor alone guards the free.
6. Destructor family: UID00011N is the ordinary source destructor. UID000124 repeats cleanup and adds MSVC delete-flag/object-free behavior; UID000121 adjusts secondary receiver views. Duplicating wrapper/thunk bodies in source is rejected.
7. Paint method name: the body is installed at primary vtable cell `0x006183d4`, in the same slot family as accepted sibling `RectangleControlPane::OnPaint`. `OnPaint()` is therefore stronger than the documentation title `RenderNumericString`.
8. Fill callback: slot `0x0069b3fc` is the broad Surface fill/invalidate callback, called after `SetDrawColor(0)` with this receiver and the copied bounds. Accepted control-source precedent uses `FillRect(&bounds)`; stale `g_pfnLockSurface` is rejected.
9. Text measurement: binary calls `m_text.c_str()` once for an inlined UTF-16 length loop, truncates `9 * length` to signed 16 bits, then calls `c_str()` again for iteration. A `short textWidth` plus `wcslen` preserves this optimizer-visible shape better than caching one pointer or using a modern container length API.
10. Alignment: integer mode `1` is right, mode `2` is centered, and all other values are left. Inventing an enum spelling is unnecessary; retaining `int m_alignment` preserves caller ABI and observed behavior.
11. Minus path: `'-'` initializes an `EPFTileContext`, looks up frame `4` in `FONTSYMB.EPF`, offsets the destination by the source frame's left/top, calls `RenderTileFrame` with mode `1`, palette `FONTSYMB.PAL`, and null options, then reverses the offset.
12. Space/slash path: UTF-16 space and slash perform no draw but always advance the destination rectangle by 9. Treating slash as a numeric glyph or separator draw is rejected.
13. Numeric glyph helper: UID0003XD has one caller, no GrafPort receiver, initializes a `0,0,9,11` context, sets stride `9`, clears encoded-mask fields, and computes `pixelData = numericGlyphs + 99 * (glyph + 10 * colorVariant - 47)`. Explicit `mov eax, esi` proves it returns the context pointer.
14. Numeric draw callback: slot `0x0069b3e8` has accepted `g_pfnBlitSprite` / `SurfaceSpriteBlitProc` support. The paint path passes this destination, glyph context/bounds, destination bounds, mode `1`, null palette, and null options.
15. Class layout: `ControlPane` occupies `0x108`; field writes/reads and `0x118` allocations close the whole derived layout. Three bytes between `char m_colorVariant` and pointer alignment are compiler padding and should not be modeled as an explicit member.
16. Vtables: three views at `0x00618390`, `0x006183f8`, and `0x00618428` are stored by constructor, ordinary destructor, and scalar wrapper. Raw vtable/RTTI arrays and explicit vptr writes are rejected source shape; the class declaration and virtual methods generate them.
17. Source placement: MiniMap creates two instances but does not own the generic control implementation. GrafPort, Surface, DATFile, EPFTileContext, and ResourceLayoutTable own dependencies only. Existing [UID:0000M2] remains the strongest file route.
18. Remaining uncertainty: exact original private spellings and whether headers were split are not recoverable, but descriptive names align with established project style and do not affect ABI or behavior. They cap perfect confidence, not first-draft readiness.
